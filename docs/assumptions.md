# docs/assumptions.md — 仕様の解釈と判断の記録

仕様(docs/spec-phase1.md / docs/spec-match-screen.md)で未定義・曖昧な点について、採用した判断と根拠を記録する。

## 点数計算エンジン(Part 1)

### 入力契約

| 項目 | 判断 | 根拠 |
|---|---|---|
| `hand` の枚数 | 副露込みで14枚相当(和了牌を含む)を正とする。13枚相当で渡された場合は `winTile` を末尾に補って14枚として扱う | 契約は「和了牌を含む純手牌」だが、仕様・受け入れ基準の入力例は13枚(`5m` 単騎の形)であり、両方の書き方を受け入れないと受け入れ基準のコマンドが意味のある結果を返せないため |
| `honba` / `kyotaku` | 省略可能な追加フィールド(非負整数、省略時 0)として受け付ける | 「本場・供託を含む点数計算」が要件だが、仕様の入力契約に該当フィールドがないため拡張した |
| `roundWind` | `ton` / `nan` に加え `sha` / `pei` も受け付ける | 契約上は `ton | nan` だが、字牌の風として妥当な値を拒否する理由がないため。東風戦/半荘戦では `ton` / `nan` しか現れない |
| `melds` / `dora` / `uraDora` / `riichi` / `ippatsu` / `situational` の省略 | 省略時はそれぞれ空配列 / `none` / `false` として扱う | 契約に「なければ空配列」とあり、他の任意項目も同様に既定値で補う方が使いやすいため |
| `winTile` が `hand` に含まれない | `invalid_input` | 和了牌を含むという契約に反する入力のため |
| 赤5の枚数 | 各色1枚まで。同色の赤5が2枚以上、または同種牌が5枚以上なら `invalid_input` | 牌は136枚・赤5は各色1枚という Part 2 の前提に合わせた |

### 出力契約

| 項目 | 判断 | 根拠 |
|---|---|---|
| `score.total` | 本場・供託を含めて和了者が受け取る合計点 | 「本場・供託を含む点数計算」の結果として最も使いやすい値のため |
| `score.payments` | `{ from, amount }` の配列。ツモは `dealer` / `non_dealer` ごとの支払額(本場込み)、ロンは `discarder` の支払額(本場込み)。供託がある場合は `{ from: "kyotaku", amount }` を追加し、常に `total === Σ amount` が成り立つ | 契約の `payments` は「ツモ時は支払い内訳」とだけあり、形式は未定義。ゲーム進行側がそのまま点数移動に使える形にした |
| 役名 | 英語スネークケース。役牌は `haku` / `hatsu` / `chun` / `seat_wind` / `round_wind` に分け、連風牌(自風=場風)は `seat_wind` と `round_wind` の両方を1翻ずつ計上する | 仕様の役名別表(付録)が未作成のため、一般的な英語表記を採用した |
| 役満の `han` | 役満は 13、ダブル役満は 26 として `yaku[].han` と合計 `han` に出力する。役満成立時は通常役・ドラを含めない | 契約上 `han` は数値であり、役満を翻数に写像する必要があるため。数え役満(13翻以上)と同じ尺度で比較できる |
| 役満の複合上限 | 複数の役満(例: 大三元+字一色)や単体のダブル役満(四暗刻単騎・国士十三面・純正九蓮・大四喜)は合計 26 翻(ダブル役満)を上限とする | 「役満の複合あり(ダブル役満まで)」を「合計でダブル役満まで」と解釈した |
| 数え役満 | 13翻以上は翻数に関わらず役満(基本点 8000)。ダブル役満にはならない | 「数え役満は13翻以上」のみが定義されており、上位区分の定義がないため |
| 平和ツモ | 20符。平和ロンは 30 符(20 + 門前ロン10) | 採用ルール「平和ツモは20符」 |
| 喰い平和形 | 副露していて符が付かない手(順子のみ・両面・非役牌雀頭)は 30 符 | 一般的なルール(喰い平和は30符) |
| 連風牌の雀頭 | 4符(自風2 + 場風2) | 天鳳・雀魂など主要な採用例に合わせた。2符とするルールもある |
| 国士無双の符 | 30符を出力する(点数には影響しない) | 役満のため符は点数に影響しない。契約上 `fu` が必須のため妥当な値を返す |
| 七対子 | 25符固定・2翻。二盃口形は通常形(二盃口)と七対子の両方を列挙し高点法で選ぶ | 採用ルール「七対子は25符固定」+ 高点法 |
| 高点法 | 面子分解・待ちの取り方・七対子/通常形の全解釈を列挙し、合計点 → 翻数 → 符の順で最大の解釈を採用する | 仕様「高点法」 |
| 後付けなし(ルール設定) | 副露している手で、和了牌を含む面子・雀頭によって初めて成立する役牌のみの手は役なしとする(その他の役は牌構成で決まるため成立済みとみなす) | 完全先付けの厳密な判定には鳴いた時点の手牌履歴が必要になるため、代表的な「役牌の後付け」を禁止する簡易ルールとした |
| ドラ表示牌 | 入力はドラそのもの(表示牌ではない)を受け取る。対局中は表示牌から `Tile.next` でドラを求めてから渡す | 契約の注記どおり |

### 役判定の詳細

| 項目 | 判断 | 根拠 |
|---|---|---|
| 役満の上限超過 | 合計が26翻を超える場合、一覧順(国士→四暗刻→大三元→四喜→字一色→清老頭→緑一色→九蓮→四槓子→天和→地和)に収まる役満だけを `yaku` に残す | 「ダブル役満まで」の上限を保ちつつ、出力の `han` と `yaku[].han` の合計を一致させるため |
| 四暗刻 | 4刻子すべてが暗刻(`open: false`)であること。双碰ロンで完成した刻子は明刻扱いのため、四暗刻はツモか単騎待ちでのみ成立(ロンの双碰は対々和+三暗刻) | 一般的なルール |
| 九蓮宝燈 | 門前・清一色で 1112345678999 を含む14枚。和了牌を除いた13枚が純正形なら純正九蓮(ダブル役満) | 一般的なルール |
| 緑一色・字一色・混老頭 | 七対子形でも成立する。清老頭は通常形のみ(老頭牌6種では七対子を作れない) | 一般的なルール |
| 混全帯么九 / 純全帯么九 | 全面子と雀頭に么九牌を含み、順子が1つ以上あること。字牌を含めば混全、含まなければ純全(排他)。全牌が么九牌なら混老頭(排他) | 一般的なルール。定義により排他関係が成立する |
| 一盃口 / 二盃口 | 同一順子2組で1盃口、同一順子が2組(同じ順子4つを含む)で二盃口。二盃口成立時は一盃口を計上しない | 一般的なルール |
| 役牌 | 槓子も刻子として数える。連風牌は `seat_wind` と `round_wind` を別々に1翻ずつ | 一般的なルール |
| ドラ | `dora` / `uraDora` の各要素について一致する牌を副露込みで数える(同じ牌が複数回並べば重ねて数える)。裏ドラはリーチ時のみ、赤ドラは副露込みの赤5枚数 | 契約の「ドラそのもの」に沿った自然な数え方 |
| 状況役のフラグ | 海底・嶺上はツモ時、河底・槍槓はロン時のみ成立。天和は親のツモ、地和は子のツモのみ。条件が合わないフラグは無視する | 一般的なルール |
| 後付けなし | 副露した手で、和了牌で完成した刻子(双碰)による役牌以外に役がなければ役なし。和了前に完成していた役牌や他の役があれば成立 | 「点数計算エンジン(Part 1)」節の判断の具体化 |

## ゲーム進行・CPU対局エンジン(Part 2)

| 項目 | 判断 | 根拠 |
|---|---|---|
| 残り山枚数 | 王牌14枚を除いたツモ可能枚数。配牌直後は70枚、親の第一ツモ後は69枚と表示する | 仕様「王牌14枚を除いたツモ可能枚数」 |
| 複数ロン | ダブロン・トリロンは採用せず頭ハネ(放銃者から見て手番順が最も近い席のみ和了) | 仕様は優先順位のみ定義。供託・本場の分配が単純になる一般的な採用例に合わせた |
| 新ドラ表示牌 | 暗槓・明槓・加槓のいずれも成立直後(嶺上ツモの前)にめくる。裏ドラはリーチ者の和了時のみ、めくれているドラ表示牌と同数 | 仕様「カン成立ごとに新ドラ表示牌を1枚追加する」に沿った最も単純なタイミング |
| カンの回数・条件 | 1局4回まで(四開槓の途中流局は非採用)。嶺上牌が残り、ツモ可能牌が1枚以上あるときのみ。カン後はツモ可能枚数が1枚減る | 途中流局はスコープ外。王牌の枚数を保つ一般的な扱い |
| 加槓と槍槓 | 加槓は槍槓の応答待ち(ロンのみ)を挟み、誰もロンしなければ嶺上ツモへ進む | 状況役「chankan」を成立させるため |
| リーチ後のカン | 暗槓は「ツモ牌で暗刻を槓子にし、待ちが変わらない」場合のみ可。加槓は不可 | 仕様「リーチ後は手替え不可」と一般的なルール |
| 喰い替え | 現物の喰い替え(鳴いた牌と同種の牌をその打牌で切る)のみ禁止。筋喰い替えは制限しない | 一般的な採用例 |
| フリテン | 自河に待ち牌があればロン不可。ロン見逃しは同巡フリテン(自分の次の打牌で解除)。リーチ中の見逃しはその局ずっとロン不可。ツモ和了はフリテンでも可 | 仕様「フリテン」節 |
| 一発・ダブルリーチ・天和・地和 | 一発はリーチ後の自分の次の打牌、または誰かの鳴き(暗槓含む)で消える。ダブルリーチ・天和・地和は「自分の最初の打牌前かつ鳴きなし」で判定 | 一般的なルール |
| 河底 | 海底牌ツモ後の打牌に対してはロンのみ可(ポン・チー・カン不可) | 一般的なルール |
| 荒牌流局 | テンパイは待ち牌の有無で判定。ノーテン罰符は場3,000点(1人テンパイ: 各1,000 / 2人: 各1,500 / 3人: 3,000)。親テンパイなら連荘、ノーテンでも本場+1で輪荘。供託は持ち越し | 仕様「流局」節 |
| 終了判定 | 最終局(東風=東4局、半荘=南4局)が子の和了または親ノーテン流局で終われば終局。最終局でも親が和了/テンパイなら連荘して続行(和了やめ・西入なし)。トビは持ち点0点未満で結果確定時に即終局(0点はセーフ) | 仕様「東4局まで / 南4局まで」「0点未満になったら終局」。和了やめ・西入は仕様にないため不採用 |
| 順位・最終ポイント | 持ち点降順、同点は起家に近い席が上位。返し点ありなら最終ポイント = (持ち点 − 返し点)/1000、オカ (返し点 − 持ち点)×4/1000 は1位に加算、ウマなし。返し点なしなら持ち点との差 | 仕様「同点は起家に近い方を上位」。ウマは仕様にないため不採用 |
| 終局時に残った供託 | 流局・トビで終局した際に卓に残った供託リーチ棒は誰にも加算しない(順位は持ち点のみで決める) | 仕様に定めがなく、加算先(1位など)を決める根拠がないため |
| 点数反映のタイミング | 和了・流局の点数は結果確定(`confirm_result`)時に反映。リーチ棒の −1,000 と供託 +1 は宣言時に即時反映 | spec-match-screen.md「結果を確定したとき…更新する」 |
| CPU自動和了なし | 初期実装では「あり」と同じく常に和了する | 仕様が「初期実装では『あり』と同じ挙動を許容」と明記 |
| CPU の鳴き | CPU は大明槓を選ばない(暗槓・加槓は行う)。危険度評価は現物・筋・字牌の見え枚数のみ。標準/上級は待ちの残り枚数が2枚未満ならリーチせずダマ | 仕様のレベル要件(打点・待ちの良さ・現物優先・危険牌評価)を満たす最小限の実装 |
| CPU の参照情報 | `TableView`(公開情報 + 自席の手牌)のみを受け取る。他家の手牌・牌山は型レベルで参照不能 | 仕様「他家の手牌や牌山の中身を参照しない」 |
| テスト用の注入 | `GameSetup.wallTiles`(136枚の並び指定)と `GameSetup.initial`(開始局・本場・供託・親・持ち点)で決定的なテストを行う。乱数は `() => number` を引数で受け取り、`libs/random` 以外で `Math.random` を使わない | rules/testing.md「乱数はフェイクで代替」 |

## 対戦画面

| 項目 | 判断 | 根拠 |
|---|---|---|
| 表示する席 | 判断を求められている人間 → 最初の人間 → 席0 の順で決める。複数の人間がいる場合はホットシート方式で手番の人間の手牌に切り替わる。全員 CPU なら席0視点の観戦になる | 仕様は人間1人+CPU3人を主とするが、4席とも操作種別を選べるため、同一端末で成立する最も単純な方式を採った |
| CPU の自動進行 | CPU の1手(打牌・鳴き応答・和了)を既定 400ms 間隔でブラウザのタイマー(`libs/scheduler`)経由で進める。テストでは 0ms | 手番の進行を目で追えるようにするため。タイマー同期は useEffect の許可ケース |
| リーチ宣言の操作 | 「リーチ」ボタンをトグルすると、リーチ宣言できる打牌だけが選べる状態になり、その打牌でリーチが成立する | 仕様「リーチ宣言(門前・テンパイ・持ち点1,000点以上・残り山4枚以上の場合のみ)」+ 打牌と同時に宣言する一般的な操作 |
| 結果表示の点数 | 「点数」は本場・供託込みの `score.total`、「点数移動」は席ごとの増減。満貫以上の区分(満貫〜ダブル役満)も併記 | spec-match-screen.md「本場・供託を含む点数移動」 |
| 対戦前の卓表示 | 設定中の持ち点・表示名・操作種別を反映した「東一局 0本場 供託0本」の卓を対戦開始前から表示する(残り山・ドラは未配牌のため「—」) | spec-match-screen.md「初期表示」 |
| 終局後 | 最終順位(順位・名前・持ち点・ポイント)を表示し、「新しい対戦」で設定画面に戻る(設定は保持) | spec-match-screen.md「終了条件を満たすと最終順位を表示する」 |

## プロジェクト構成

| 項目 | 判断 | 根拠 |
|---|---|---|
| `app/` の配置 | `mahjong/src/app/` に移動 | rules/architecture.md のフォルダ構造が `src/app/` を前提としているため |
| CLI の実行方式 | `node --import ./scripts/register-ts-resolver.mjs src/cli/calc.ts`。Node 標準の型ストリップ実行に、拡張子省略・ディレクトリ import・`@/` エイリアスを解決する自前フック(依存追加なし)を組み合わせる | 外部ランタイム依存を追加せずに、Next.js と同じ import 記法のソースを CLI から直接実行するため |
| `src/types/` の参照 | `domains/` からも `src/types/` の純粋な型を import してよい(依存を持たない層のため) | rules/architecture.md は domains からの types 参照を明示していないが、ロジックを持たない型は循環・ドメイン知識流入の懸念がなく、入出力契約の型を1か所に置く方が重複を避けられる |
| tsconfig | `verbatimModuleSyntax` / `erasableSyntaxOnly` を有効化 | Node の型ストリップ実行で動く構文(型 import の明示、enum 等の不使用)を型チェックで保証するため |
