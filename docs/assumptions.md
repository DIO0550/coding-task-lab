# docs/assumptions.md — 仕様の曖昧点に対する判断と根拠

`docs/spec-phase1.md` / `docs/spec-match-screen.md` の解釈に迷った点、および実装上確定させた事項を記録する。
各項目は「判断」と「根拠」をセットで記す。実装(mahjong/)はこの文書の決定に従う。

## 配置・アーキテクチャ

### A-1. `docs/assumptions.md` の配置

- **判断**: リポジトリルートの `docs/`(`docs/spec-phase1.md` と同階層)に置く。
- **根拠**: 仕様書本体と同じ場所に置くことで参照しやすい。プロンプト/仕様の参照パス `docs/assumptions.md` とも一致する。

### A-2. Next.js の `app/` はプロジェクト直下に置く

- **判断**: `rules/architecture.md` は `src/app/` を図示するが、実リポジトリの Next.js ルーティングは `mahjong/app/`(プロジェクト直下)に既存。これを維持し、`domains/services/features/components/hooks/libs/utils/types` を `mahjong/src/` 配下に置く。
- **根拠**: 既存構成(create-next-app 由来)を尊重し破壊を避ける。依存方向 `app → features → services/domains` は保たれる。

### A-3. 点数計算/ゲーム進行/CPU を `domains/` に配置(services ではなく)

- **判断**: scoring(点数計算オーケストレータ)・game(進行エンジン)・cpu(対局AI)を `src/domains/` 配下のドメインとして実装する。
- **根拠**: `rules/architecture.md` は「services は domains/types/utils のみ import 可」とし、service→service を許さない。ゲーム進行は点数計算を再利用する必要があるため、両者を service にすると依存できない。domains は他 domain を import 可(一方向・循環禁止)なので、domains に置くことで規約を満たしつつ再利用できる。features はこれら domains を直接 import してよい(規約で明示的に許可)。

### A-4. import は `.ts`/`.tsx` 拡張子付き相対パスに統一

- **判断**: `src/` 配下のモジュール間 import は拡張子付き相対パス(例 `import { Tile } from "../tile/index.ts"`)を用いる。`@/` エイリアスは `domains/services/cli` では使わない。`tsconfig.json` に `allowImportingTsExtensions: true` を追加する。
- **根拠**: CLI(`pnpm calc`)は `node --experimental-strip-types` で `src/cli/calc.ts` を直接実行する。Node の型ストリップは拡張子なし相対 import と `@/` エイリアスを解決できず、`.ts` 拡張子付き相対 import のみ解決可能。Next.js(Turbopack) build・Vitest・`tsc` は `.ts` 拡張子付き import を解決できることを実測で確認済み。全経路で解決可能な唯一の表記が拡張子付き相対パス。

## 点数計算エンジン(Part 1)

### S-1. `hand` の枚数と `winTile` の扱い(最重要)

- **判断**: `hand` は「和了牌を含む完成手(14枚相当)」でも「和了牌を除く手(13枚相当)」でも受理する。副露 `melds` を m 個持つ手の面前部分の期待枚数を `expected = 14 - 3*m` とし、
  - `hand.length === expected` のとき → `hand` は和了牌を含む(そのまま使用)。
  - `hand.length === expected - 1` のとき → `hand` に `winTile` を加えて完成手とする。
  - それ以外 → `invalid_input`。
  さらに完成手には必ず `winTile` が含まれていなければならない(含まれなければ `invalid_input`)。
- **根拠**: 仕様本文は「hand は和了牌を含む純手牌」とするが、仕様・プロンプトの例 `["1m","2m","3m","4p","5p","6p","7s","8s","9s","ton","ton","ton","5m"]`(13枚)+`winTile:"5m"` は 13枚であり、和了牌を加えて初めて 14枚(123m/456p/789s/ton³/5m5m)の和了形になる。両表現を受理することで仕様本文と例の双方に矛盾なく対応する。カンは4枚だが手牌14枚勘定では1面子(3枚相当)として扱い、`expected = 14 - 3*m` とする(標準ルール)。

### S-2. 牌の内部表現と赤5

- **判断**: 牌は `{ suit: "m"|"p"|"s"|"z"; rank: number; red: boolean }`。字牌は suit=`z`、rank は `ton=1,nan=2,sha=3,pei=4,haku=5,hatsu=6,chun=7`。赤5は `0m/0p/0s` を rank=5・`red=true` として取り込む。牌の同一性(面子構成・待ち・役判定)では red を無視し、ドラ加算でのみ red を数える。
- **根拠**: 赤5は牌姿としては通常の5と同一で、ドラ枚数だけ増やす。suit/rank/red の分離で「形は同じ・ドラだけ加算」を自然に表現できる。

### S-4. ドラ・裏ドラ・赤ドラの出力表現

- **判断**: ドラは役ではないが、出力 `yaku[]` に `{name:"dora",han:N}`・`{name:"ura_dora",han:N}`・`{name:"aka_dora",han:N}`(該当枚数>0のもののみ)を含め、`han` 合計に加算する。役(ドラを除く)が1つも無ければ `no_yaku`。
- **根拠**: 出力契約は `yaku` と `han` のみを持ち、ドラを別項目に分けられない。ドラ枚数を `yaku` に含めることで `han` 合計と整合させる。ドラのみで和了できない(役なし)ルールも守れる。

### S-5. 符計算

- **判断**: 副底20符 + 待ち(両面0/嵌張・辺張・単騎2)+ 面子(明刻: 中張2・幺九4、暗刻: 中張4・幺九8、明槓: 中張8・幺九16、暗槓: 中張16・幺九32)+ 雀頭(役牌2、連風牌2、それ以外0)+ 和了(門前ロン10、ツモ2)。合計を10符単位に切り上げ。例外: 平和ツモ=20符固定、七対子=25符固定(切り上げなし)、平和ロン=30符(20+門前ロン10)、喰い平和形のロンは最低30符(20+ツモ以外…)は下記 S-6 の30符ルールで扱う。
- **根拠**: 標準リーチ麻雀の符計算。仕様の採用ルール(平和ツモ20符・七対子25符固定・切り上げ満貫なし)に一致。連風牌(場風=自風の雀頭)は2符とする(4符説もあるが標準の2符を採用)。

### S-6. 喰い平和形(鳴き20符)ロンの扱い

- **判断**: 面子・待ち・雀頭がすべて0符になる鳴き手のロン(いわゆる喰い平和形)は、副底20符のみで10符未満になるため最低30符とする(20符+10符の底上げ)。ツモの場合は20符+ツモ2符=22→切り上げ30符。
- **根拠**: 20符ロンは存在しないため、標準ルールに従い30符へ引き上げる。仕様に明記はないが一般的な標準処理。

### S-7. 点数計算(基本点・満貫以上・支払い形式)

- **判断**:
  - 基本点 `base = fu * 2^(2+han)`。`base > 2000` は満貫として `base=2000`(切り上げ満貫なしのため 4翻30符=1920 等は満貫にしない)。
  - 翻数による固定: 5翻=満貫(2000)/6–7翻=跳満(3000)/8–10翻=倍満(4000)/11–12翻=三倍満(6000)/13翻以上=数え役満(8000)。役満(実役)は 8000×(役満倍数)。
  - 子ロン=`ceil100(base*4)`、親ロン=`ceil100(base*6)`、子ツモ=親`ceil100(base*2)`+子`ceil100(base)`×2、親ツモ=子`ceil100(base*2)`×3。
  - 本場: ロンは放銃者が +300×本場、ツモは各支払者が +100×本場。供託: 和了者が全リーチ棒(1000×本数)を取得。
  - 出力 `score.total` は「和了者が支払者から得る合計(手の点+本場)」。供託(リーチ棒)は含めない(ゲーム進行側で加算)。`payments` は `{from, amount}[]`:
    - ロン: `[{from:"ron", amount: total}]`
    - 子ツモ: `[{from:"tsumo_dealer", amount:親支払}, {from:"tsumo_non_dealer", amount:子1人あたり支払}]`
    - 親ツモ: `[{from:"tsumo_non_dealer", amount:1人あたり支払}]`
- **根拠**: 標準点数計算。CLI 入力には本場・供託フィールドが無いため、CLI では本場0・供託0として計算し、本場・供託の実加算はゲーム進行エンジンが担う(仕様「本場・供託を含む点数計算」はエンジン側で満たす)。`payments` 形式は役割ベースで、CLI が座席全体を知らなくても表現できるようにした。

### S-8. 判定の優先順位(valid:false の理由)

- **判断**: `invalid_input`(牌表記不正・枚数不整合・JSON不正)→ `not_winning_hand`(和了形でない)→ `no_yaku`(和了形だが役なし)の順に判定する。
- **根拠**: 入力が壊れていれば形の判定に進めない。形が成立して初めて役の有無を問える。

### S-9. 高点法のタイブレーク

- **判断**: 複数の和了形・待ち解釈のうち、まず合計点(total)が最大の解釈を採る。total 同点なら翻数、次に符が大きい解釈を採る。
- **根拠**: 仕様「最も点数が高くなる解釈」。同点時の副次基準(翻→符)は一般的慣行。

### S-10. 入力パースの詳細(基盤実装で確定)

- **判断**:
  - `dora`/`uraDora` のみ省略可(欠落時は空配列)。`hand`/`melds`/`winTile`/`winType`/`seatWind`/`roundWind`/`riichi`/`ippatsu`/`situational` は必須(欠落・型不正は `invalid_input`)。
  - 同一牌種5枚以上は `invalid_input`(枚数不整合)。
  - `roundWind` は `ton`|`nan` のみ受理。
  - リーチ無しでの `ippatsu:true`・`uraDora` 指定など意味的不整合はパースでは拒否せず、役判定側で無視/扱いを決める。
  - `ScoreRequest.parse` は構造検証のみで和了形判定はしない。`not_winning_hand` は `Hand.decompose` が空のときにオーケストレータが返す。
  - `StandardForm.groups` は面前面子(牌種昇順、同一牌種は刻子→順子)が先、副露面子が末尾。`pair` は groups に含めず別フィールド。`WinContext.agariPositions` は副露面子を和了完成位置から除外する(和了牌で副露は完成しないため)。
- **根拠**: 基盤ドメイン(tile/meld/hand/win-context)の実装・検証(130テスト・乱数2999手で decompose と shanten の和了判定一致)を通じて確定した仕様詳細。後続の役判定・符点数・オーケストレータはこの前提に従う。

## ゲーム進行エンジン(Part 2)

### G-1. 牌山・王牌・ドラ

- **判断**: 全136枚。赤ドラありのとき 5m/5p/5s 各1枚を 0m/0p/0s に置換。開局時にシャッフルし、末尾14枚を王牌とする。ドラ表示牌は王牌から1枚公開し、`Tile.doraFromIndicator`(数牌は次の数、9→1、字牌は 東→南→西→北→東、白→發→中→白)でドラを決める。カン成立ごとに新ドラ表示牌を1枚追加(最大4回=表示5枚)、嶺上牌は王牌から補充。裏ドラは王牌のドラ表示牌の下段。
- **根拠**: 標準の王牌14枚・ドラ表示手順。

### G-2. 配牌・残り山

- **判断**: 各家13枚配牌。残りツモ可能枚数=136−14(王牌)−13×4(配牌)=70枚から開始し、ツモ/嶺上で減る。画面表示の「残り山」はこのツモ可能枚数。
- **根拠**: 標準。荒牌流局は残り0で判定。

### G-3. 鳴き優先順位・チー

- **判断**: 打牌への宣言優先は ロン > ポン/明カン > チー。ロンは複数同時(頭跳ねは起家に近い上家優先)。チーは下家(打牌者の次家)のみ。
- **根拠**: 仕様「ロン > ポン/カン > チー」。頭跳ねは標準(上家優先)。

### G-4. リーチ成立条件・フリテン

- **判断**: リーチは 面前・テンパイ・持ち点1000以上・残り山4枚以上 で宣言可。宣言で1000点を供託へ。以後は和了牌以外ツモ切り。フリテン(自分の河に待ち牌がある/リーチ後に和了牌を見逃した)ではロン不可、ツモは可。
- **根拠**: 仕様の記述に一致。

### G-4b. リーチ棒の順位精算上の帰属

- **判断**: トビ・終局判定における持ち点は「場に出ている供託(未回収リーチ棒)を差し引いた実点」で行う。最終順位は素点(持ち点)で決定し、供託が残っていれば最終的にトップが回収する。
- **根拠**: 仕様はトビ=持ち点0未満。リーチ棒を出した時点で持ち点は減っているため実点で判定できる。

### G-5. 流局・連荘・輪荘

- **判断**: 荒牌流局時、テンパイ者とノーテン者で場3000点を分配(テンパイ1人:各ノーテン1000ずつ受取=1000/1500/3000、全員テンパイ/全員ノーテンは移動なし)。親テンパイ=連荘(本場+1)、親ノーテン=輪荘(親交代・本場+1)。供託は次局へ持ち越す。途中流局(九種九牌・四風連打・四家立直・四槓散了)は採用しない。
- **根拠**: 仕様「ノーテン罰符(場3,000点)」「親テンパイなら連荘、ノーテンなら輪荘」。スコープ表で途中流局は「含まない」。

### G-6. 連荘・親移動・終了・順位

- **判断**: 親和了=連荘・本場+1。子和了=親を下家へ移動・本場0・次局。東風戦=東4局まで、半荘戦=南4局まで(オーラス親和了による延長は無し、規定局消化で終了)。いずれかの持ち点が0未満でトビ終局。終局時、持ち点降順で順位、同点は起家(東家)に近い席を上位とする。ウマ・オカは採用せず素点順位のみ。
- **根拠**: 仕様「東風=東4/半荘=南4」「持ち点で順位、同点は起家に近い方」。ウマ・オカは仕様に指定が無いため不採用と決定(返し点・持ち点設定は表示・トビ判定に用いるが順位はあくまで素点)。

### G-7. CPU 自動和了「なし」設定

- **判断**: 初期実装では「CPU自動和了: なし」でも「あり」と同じく、役があれば必ず和了宣言する挙動とする。
- **根拠**: 仕様が「初期実装では『あり』と同じ挙動を許容し、判断を assumptions に記録する」と明記。

### G-8. 乱数の注入(純粋性の担保)

- **判断**: 牌山シャッフルの乱数は `src/libs/` のラッパ(seed 指定可能な PRNG)経由で供給し、`domains/game` の洗牌関数は乱数生成器を引数で受け取る純粋関数とする。テストは決定的 seed / 固定牌山を注入して検証する。
- **根拠**: `rules/coding.md` は domains での I/O を禁止。乱数を libs に閉じ込め注入することで domains を純粋に保ち、テスト可能にする。

## 対戦画面(spec-match-screen)

### U-1. 席・風の割り当てと表示

- **判断**: 座席は起家(東家)を席0とし、東→南→西→北の順に時計回り(次家=下家)。各局で親が移動しても席の物理配置は固定し、風(場風/自風)は親位置に応じて割り当てる。人間はデフォルトで席0(東家)。
- **根拠**: 一般的な麻雀 UI。仕様「風: 東/南/西/北」「親がどのプレイヤーか表示」。

### U-2. 初期表示

- **判断**: 対戦画面を開いた直後(未開始)は東一局・0本場・供託0本・各家25000点・半荘戦の開始状態を静的表示する。設定変更は「対戦開始」前に行う。
- **根拠**: 仕様「初期表示」表に一致。

### U-3. CPU 自動進行のペーシング

- **判断**: CPU の手番は一定間隔(約600ms)で自動進行し、人間が視認できるようにする。タイマーは `src/libs/` 経由または feature 内 effect で管理し、クリーンアップする。
- **根拠**: 仕様「手番が自動で進行」「CPU が自動で行動」。視認性のため待機を入れる。UI 都合の外部同期(タイマー)は `rules/hooks.md` が許可する useEffect 用途。

### U-4. 結果表示・点数反映

- **判断**: 和了/流局は操作から自動発生し、結果(和了者・放銃者・種別・役・翻・符・点数移動・親継続)をモーダルで表示。「確定(次局へ)」操作で点数反映し次局へ進む。手動結果入力は設けない。
- **根拠**: 仕様「手動で結果を入力する方式は採用しない」「確定すると点数反映のうえ次局へ進む」。

## CPU 対局 AI(Part 2)

### C-1. `Cpu.decide` の入出力契約

- **判断**: CPU の行動決定 API は `Cpu.decide(view: PlayerView, level: CpuLevel): Action`(`src/domains/cpu`)。返す Action は必ず `view.legalActions` の要素であり、同一 view+level には常に同一の Action を返す(乱数・時刻不使用の純粋関数)。`legalActions` が空の view(手番・宣言機会でない席)で呼ぶのは呼び出し誤りとして例外を投げる。
- **根拠**: 仕様「CPU の行動は卓の公開情報と自分の手牌のみに基づいて決定する」。`PlayerView` がまさにその情報のみを持つ。呼び出し側は `Game.currentActor` が返した席についてのみ decide を呼べばよい。

### C-2. 全レベル共通の和了最優先

- **判断**: `legalActions` に `tsumo`/`ron` があれば必ずそれを返す(「CPU自動和了: なし」設定でも同じ。G-7 のとおり)。
- **根拠**: G-7。エンジンは役ありの場合しか tsumo/ron を合法手にしないため、常に宣言してよい。

### C-3. 鳴き判断のルール前提(喰いタン)

- **判断**: `PlayerView` にルール設定(kuitan 等)は含まれないため、鳴き判断の「タンヤオが見込める」は仕様の採用ルール「喰いタン: あり」を前提に評価する。
- **根拠**: 仕様の採用ルール。誤って役無しになってもエンジンが和了を許さないだけで進行は破綻しない。

### C-4. カンの方針

- **判断**: 明カンは全レベルで宣言しない(新ドラ追加リスクに対し利得が薄い)。暗槓・加槓は「カン後にシャンテンが悪化しない」場合のみ宣言する。標準・上級は他家リーチ中はカンしない。リーチ中の自分は暗槓を宣言する(待ち不変は legalActions 側が保証)。
- **根拠**: 仕様のレベル表はカン方針を規定しないため、妥当で決定的な方針として確定。

### C-5. リーチ判断

- **判断**: 入門はリーチ可能なら常に宣言。標準・上級は待ちの未見枚数(自分から見えない残り枚数)が0のテンパイでは宣言しない。宣言打牌は「待ちの未見枚数が最大」になる牌を選ぶ。上級は C-6 で降りると判断した場合は宣言しない。
- **根拠**: レベル表「入門: テンパイしたら常に宣言」「標準: 打点・待ちの良さを考慮」の最小の具体化。

### C-6. 押し引き

- **判断**: 入門は考慮しない(他家リーチ中も自分の牌効率で切る)。標準は他家リーチ中、手内に現物(そのリーチ者の河にある牌)があればシャンテンを崩しても現物を切り、無ければ自分の効率牌を切る。上級は「テンパイを保てる かつ 打点目安(手内のドラ・赤の枚数+面前なら+1)が2以上」なら押し、それ以外はベタ降り(危険度順: 現物 > 字牌(見えている枚数が多いほど安全) > リーチ者の河のスジ > 非スジ。数牌は端に近いほど安全)する。
- **根拠**: レベル表「標準: 他家リーチ時に現物を優先」「上級: 危険牌評価と降り判断を行う」の具体化。差異(入門は降りない/標準は現物優先/上級は降り・押し判断)がテストで観測できる。
