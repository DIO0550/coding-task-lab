# docs/assumptions.md — 仕様の解釈と判断の記録

`docs/spec-phase1.md` / `docs/spec-match-screen.md` / `AGENTS.md` で明記されていない、
または解釈が分かれる事項について、実装で採用した判断とその根拠を記録する。

## 1. 点数計算エンジン(Part 1)

### 1.1 入力JSONの拡張: `honba` / `riichiSticks`

仕様の入力JSONには本場・供託の項目がないが、受け入れ基準に「本場・供託を含む点数計算」が
含まれるため、任意項目として `honba`(本場数)と `riichiSticks`(供託リーチ棒の本数)を追加した。
どちらも省略時は `0`。既存の入力例はそのまま動作する。

### 1.2 手牌は13枚形・14枚形の両方を受け付ける

仕様本文は「hand は和了牌を含む純手牌」と定義しているが、仕様および実装依頼に載っている入力例は
和了牌 `5m` を含めても13枚しかない(`hand` 13枚 + `melds` 0)。
例が動作しないままでは受け入れ基準を満たせないため、次のとおり両方を受け付ける。

- `hand + melds*3 == 14`: 仕様本文どおり、和了牌を含む形として扱う(和了牌が `hand` に無ければ `invalid_input`)。
- `hand + melds*3 == 13`: 和了牌を含まない形として扱い、`winTile` を加えて14枚にする。
- それ以外: `invalid_input`。

13枚形と14枚形は枚数で一意に区別でき、解釈が衝突しない。

### 1.3 出力の役名一覧と `dora` / `ura_dora` / `aka_dora`

仕様の役名表(付録)は未作成のため、`src/domains/yaku/yaku.ts` の `YakuName` を正式な一覧とする
(詳細は [rules/cli-contract.md](../rules/cli-contract.md))。
ドラ・裏ドラ・赤ドラは役ではないが、翻数の内訳を出力に含める必要があるため
`{"name": "dora", "han": 枚数}` の形で `yaku` 配列に含める。
「役なし」の判定(`no_yaku`)ではドラを除いて判定する。

### 1.4 `score.total` と `score.payments` の意味

- `total`: 和了者の収入合計。**本場と供託を含む**。
- `payments`: 支払い者ごとの内訳。**本場を含み、供託は含まない**(供託は場に出ている点棒のため)。
  - ロン: `{"from": "discarder", "amount": N}` の1件。
  - 子のツモ: `{"from": "dealer"}` 1件 + `{"from": "non_dealer"}` 2件。
  - 親のツモ: `{"from": "non_dealer"}` 3件。
- `total == sum(payments) + 1000 * riichiSticks` が常に成り立つ。

出力には仕様に無い `score.limit`(`none` / `mangan` / `haneman` / `baiman` / `sanbaiman` /
`kazoe_yakuman` / `yakuman`)も含める。画面の結果表示で使うための追加情報で、既存項目は変更していない。

### 1.5 符計算の細部

| 事項 | 採用 | 根拠 |
|---|---|---|
| 連風牌(場風=自風)の雀頭 | **2符** | 4符とする流派もあるが、オンライン麻雀で最も普及している2符を採る |
| 国士無双の符 | 25符(便宜値) | 役満のため点数に影響しない。出力の一貫性のために固定値を返す |
| 喰い平和形(20符で計算が終わる副露手) | **30符** | 平和は門前限定のため20符のまま確定させない一般的な扱い |
| 平和ツモ | 20符(ツモ2符なし) | 仕様の採用ルールに明記 |
| 七対子 | 25符固定 | 仕様の採用ルールに明記 |
| ロンで完成した刻子 | 明刻として符計算・三暗刻判定を行う | 一般的な扱い |

### 1.6 役満まわり

- **ダブル役満**とする役: 国士無双十三面待ち / 四暗刻単騎待ち / 純正九蓮宝燈 / 大四喜。
- 役満が複合した場合は倍数を合計し、仕様の「ダブル役満まで」に従って **上限2倍**に丸める
  (例: 四槓子 + 四暗刻単騎 = 3倍 → 2倍)。
- 役満成立時は通常役とドラを一切加算せず、役満のみを出力する。
- 翻数は `13 × 倍数` として出力する(数え役満と同じ13翻を1倍とする)。
- 数え役満は13翻以上(仕様どおり)。役満の複合上限とは別扱い。

### 1.7 役の複合可否

- **混老頭とチャンタは複合する**(全ブロックが么九牌を含むため両方の条件を満たす)。
- **七対子とチャンタ/純チャンは複合しない**(面子手ではないため)。一方、七対子と混老頭・字一色・
  清老頭・緑一色は複合する。
- 一盃口が2組成立する場合は二盃口のみとし、一盃口は重複して数えない。
- 連風牌の刻子は場風・自風の2つの役として数える(合計2翻)。
- 天和・地和は入力の `situational` をそのまま信頼する。海底・嶺上は自摸和了時のみ、
  河底・槍槓は栄和時のみ有効とし、和了種別と矛盾する指定は無視する。

### 1.8 高点法

同じ手牌に複数の解釈(面子の取り方・待ちの取り方)がある場合、
**合計点 → 翻数 → 符** の優先順で最も高い解釈を採用する。
役が成立しない解釈は候補から除外する。

## 2. ゲーム進行・CPU対局(Part 2)

### 2.1 王牌の構成

王牌14枚の内訳を「ドラ表示牌5枚 + 裏ドラ表示牌5枚 + 嶺上牌4枚」とした。
ツモ可能枚数は `136 - 14(王牌) - 52(配牌) = 70枚`。カンが成立するごとに
嶺上牌を1枚使い、ツモ可能枚数が1枚減り、ドラ表示牌が1枚増える(最大5枚)。

### 2.2 ダブロンは採用しない(頭ハネ)

複数人が同時にロンを宣言できる場合、放銃者から見て最も近い(下家側の)プレイヤーのみが和了する。
仕様に規定がなく、点数移動と本場処理が単純になるため。三家和による途中流局も採用しない。

### 2.3 フリテン

仕様の「自分の捨て牌に和了牌が含まれる場合はロン不可」「リーチ後の見逃しは以降ロン不可」に加えて、
一般的な**同巡内フリテン**を採用した。ロンできる牌を見逃した場合、自分の次のツモまでロンできない。
リーチ中の見逃しは永続フリテンとする。

### 2.4 リーチの条件と制限

宣言できるのは「門前 + テンパイ + 持ち点1,000点以上 + 残り山4枚以上」。宣言時に1,000点を供託へ出す。
リーチ後はツモ切りのみ(和了・暗槓を除く)。リーチ後の暗槓は**待ちが変わらない場合のみ**許可し、
加槓・大明槓・チー・ポンは不可とする。

### 2.5 途中流局・特殊ルールは実装しない

仕様のスコープ外(「含まない」)のため、九種九牌・四風連打・四槓散了・四家立直による途中流局は
実装しない。アガリやめ・テンパイやめ、現物食い替えの禁止も実装していない。

### 2.6 「CPU自動和了: なし」の挙動

仕様 Part 2 に「初期実装では『あり』と同じ挙動を許容する」と明記されているため、
設定値に関わらず CPU は和了可能(役あり)なら必ずツモ/ロンを宣言する。
設定項目自体は対戦開始設定に表示・保持する。

### 2.7 「喰いタンなし」「後付けなし」の解釈

対戦開始設定で選択できるため、点数計算側に反映できるようにした。

- **喰いタンなし**: 副露している手のタンヤオを役として数えない(結果として役がなければ和了不可)。
- **後付けなし**: 副露している手で、ドラを除く成立役が役牌のみ、かつ**和了牌がその役牌の刻子を
  完成させた**場合は和了できない。完全先付け・片アガリ禁止の流派差が大きいため、
  最も一般的に「後付け」と呼ばれる形だけを対象とする。

いずれも既定値は「あり」(仕様の採用ルールどおり)で、CLI(`pnpm calc`)は常に「あり」で計算する。

### 2.8 CPU の行動決定

- 判断材料は `PlayerView`(自分の手牌 + 卓の公開情報)のみ。他家の手牌・山の中身は参照しない。
- 乱数を使わず決定的に動く(同じ状況・同じレベルなら常に同じ行動)。
- 受け入れ枚数は「自分の手牌・全員の河(鳴かれた牌を除く)・全員の副露・ドラ表示牌から見えている
  枚数」を4枚から引いて数える。
- 現物は「そのリーチ者自身の河にある牌」のみとする(リーチ後に他家が通した牌は
  `PlayerView` から打順を再構成できないため含めない)。
- 押し引きの発動条件は「他家リーチ中 かつ 自分が2シャンテン以上」。

### 2.9 終局判定

- 東風戦は東4局、半荘戦は南4局を終えたら終局。親の連荘中は同じ局が続く。
- いずれかの持ち点が0点未満になったら終局(トビ)。判定は局の結果を確定した時点で行う。
- 同点の順位は起家に近い席を上位とする(仕様どおり)。

## 3. 実装・構成上の判断

### 3.1 相対 import に `.ts` / `.tsx` 拡張子を必須とする

受け入れ基準の `echo '<入力JSON>' | pnpm --silent calc` を**外部ランタイム依存を追加せずに**満たすため、
CLI は Node.js 標準の型剥がし(`node --experimental-strip-types`)で実行する。
Node.js の ESM 解決は拡張子の省略とパスエイリアスに対応しないため、
`@/` エイリアスを使わず、すべての相対 import に拡張子を付ける方針とした
(`tsconfig.json` に `allowImportingTsExtensions` を追加)。
Next.js(Turbopack)・tsc・Vitest のいずれでも解決できることを確認済み。

### 3.2 `app/` を `src/app/` へ移動

`rules/architecture.md` のフォルダ構成が `src/app/` を指定しているため、
Next.js が公式にサポートする `src/app` へ移動した。

### 3.3 services 間の import を限定的に許可

`rules/architecture.md` は services が import してよい対象を domains / types / utils と列挙しているが、
ゲーム進行(`services/game`)は和了時に点数計算(`services/score-calculation`)を必要とする。
点数計算を重複実装しないという仕様要件を優先し、**services 間の import を
「公開API(`index.ts`)経由・循環なし」に限って許可**した。
現在の依存は `game → score-calculation` の1方向のみ。

### 3.4 `src/cli/` の位置づけ

`rules/architecture.md` に記載のないフォルダだが、`app/` と同じ「エントリポイント層」として扱う。
標準入出力の処理のみを持ち、判定・計算は `services/score-io` に委譲する。

### 3.5 乱数とタイマーの扱い

- 牌山のシャッフルに使う乱数は `types/rng.ts` の `Rng`(`() => number`)として注入する。
  実装は `libs/random`(`Random.system()` / `Random.fromSeed()`)にあり、
  domains / services は乱数の実体を import しない。テストは種を固定して決定的に検証する。
- CPU の自動進行に使うタイマーは `libs/timer` に閉じ込め、`hooks/use-timeout` 経由で使う。

### 3.6 対戦画面の自動進行

`Game.autoStep(session)` は「人間の入力を必要としない進行」を1手だけ進め、
人間の操作待ちなら `null` を返す。画面はこの戻り値が `null` でない間だけタイマーを予約して
自動進行させる。既定の間隔は550ms(`MatchScreen` の `autoAdvanceMs` で変更可能。テストは0ms)。

### 3.7 リーチ宣言の操作手順

画面の「リーチ」ボタンは宣言のみを行わず、**リーチ宣言牌の選択モード**へ移る。
続けて手牌からテンパイを保てる牌を選ぶとリーチが成立する。
リーチ宣言と打牌は不可分のため、1操作にまとめるとどの牌で宣言したかを表現できないため。
