### hand の枚数の解釈

仕様は「hand は和了牌を含む純手牌」と定義するが、仕様・受け入れ基準の入力例は13枚(和了牌が1枚不足)である。両者を整合させるため、`hand` の枚数が `14 - 3×副露数` の場合はそのまま、`13 - 3×副露数` の場合は「和了牌が含まれていない形式」と解釈して `winTile` を補って計算する。それ以外の枚数は `invalid_input`。

### 入力JSONの追加フィールド(本場・供託)

入力JSON契約に本場・供託のフィールドが定義されていないが、仕様は「本場・供託を含む点数計算」を要求している。そのため入力JSONに**省略可能**なフィールド `honba`(number, 既定0)と `kyotaku`(供託本数, number, 既定0)を追加で受け付ける。省略時は仕様の入力例と完全互換。

### payments の形式

仕様では `"payments": [ ... ]` と形式が未定義のため、以下を定義する。

- 各要素は `{ "from": string, "amount": number }`。
- ツモ(子): `{"from":"dealer"}` 1件と `{"from":"non_dealer"}` 2件。
- ツモ(親): `{"from":"non_dealer"}` 3件。
- ロン: `{"from":"discarder"}` 1件。
- 供託がある場合は `{"from":"pot","amount":供託本数×1000}` を追加する。
- 本場加算はツモでは各支払者に100点×本場、ロンでは放銃者に300点×本場を上乗せする。
- `total` は payments の合計(=和了者が受け取る点数)と一致する。

### 役満の翻数表現

出力の `han` は数値であるため、役満は1つにつき13翻(ダブル役満は26翻)として表現する。点数計算は翻数ではなく役満単位(基本点8000×単位)で行う。役満複合時は units 合計を2でキャップする(「ダブル役満まで」の解釈: **合計上限がダブル役満**)。

### 役満時の符

役満は符が点数に影響しないため、標準形は分解に基づく符を、国士無双は符の定義が存在しないため `0` を出力する。七対子役満(字一色七対子等)は25符。

## 点数計算ルールの詳細解釈

- **ダブル役満になる役**: 国士無双十三面待ち、四暗刻単騎、純正九蓮宝燈(9面待ち)、大四喜。それ以外は単一役満。根拠: 一般的な採用例。
- **連風牌の雀頭の符**: 自風+2符、場風+2符で重複時は4符。根拠: 天鳳等の主要実装。
- **喰い平和形のロン**: 副露ありで計20符となるロン和了は30符として扱う(一般的な喰い平和30符ルール)。
- **切り上げ満貫なし**: 基本点が2000を超える場合のみ満貫に切り上げ(30符4翻=7700/11600、60符3翻=7700/11600)。
- **数え役満**: 13翻以上は数え役満(基本点8000)。役満との複合はしない(役満成立時は通常役・ドラを数えない)。
- **五重複牌チェック**: 赤5(`0m`)は5と同一牌として枚数制限(各牌4枚、赤は各色1枚)を検査する。
- **入力の整合性検査**: 以下は `invalid_input` とする。
  - 純手牌の枚数が `14 - 3×副露数` でない。
  - `winTile` が `hand` に含まれない。
  - 副露の構成が不正(チーが順子でない等)。
  - リーチ指定があるのに門前でない(暗槓は門前扱い)。
  - 一発指定があるのにリーチしていない。
  - `tenhou` は親・ツモ以外、`chihou` は子・ツモ以外で指定された場合。
  - 同名牌5枚以上(赤含む)。
- **天和・地和**: `situational` の入力を信頼して成立させる(付随条件: 天和は親のツモ、地和は子のツモ)。天和/地和時のリーチ・一発は矛盾入力として `invalid_input`。
- **槍槓とロン**: `chankan` は `winType: "ron"` と組み合わせる。
- **海底(haitei)はツモ、河底(houtei)はロン**と組み合わせる。矛盾は `invalid_input`。

AGENTS.md の規約一覧に `rules/cli-contract.md` が記載されているがファイルが存在しない。CLI契約は prompt.txt および docs/spec-phase1.md の入出力契約に従って実装した。

## アーキテクチャ上の判断

- **点数計算のオーケストレーション(`Scoring`)を `src/domains/scoring/` に配置**。ゲーム進行エンジン(`services/game/`)から点数計算を再利用する必要があるが、規約上 services 間の import は許可されていない(services は domains/types/utils のみ import 可)。点数計算は「和了結果」というドメイン概念のコンパニオンオブジェクトとして表現できるため、domains に配置し、services/game と services/score-calculator の双方から再利用する(重複実装の禁止に適合)。
- **乱数・タイマーは libs 経由で注入**。`domains/` `services/` は純粋関数のみで構成し、乱数(牌山シャッフル)は `libs/random/` の RNG を引数注入、CPU手番の自動進行タイマーは `libs/timer/` のラッパーを使用する。

## ゲーム進行の解釈

- **複数ロン(ダブロン)**: 採用せず頭ハネ(放銃者から反時計回りで最も近い和了者のみ成立)。結果表示・点数移動が単一和了者で一貫するため。
- **オーラスの連荘**: 東風戦の東4局・半荘戦の南4局で親が連荘した場合、対局は継続する。終局は最終局で輪荘が発生した時点、またはトビ。アガリやめ・テンパイやめは採用しない。
- **供託の残留**: 終局時に供託が残っている場合はトップ(1位)が回収する。
- **リーチ後の暗槓**: 直前のツモ牌の暗槓のみ、かつ待ちが変化しない場合に許可する(送りカン禁止)。
- **槍槓**: 加槓に対してのみロン(槍槓)を認める。暗槓に対する国士無双の槍槓は採用しない。
- **嶺上牌と海底**: カンのたびに嶺上牌を王牌から補充し、生牌山の末尾1枚を王牌へ移す(ツモ可能枚数が1減る)。残り山0枚のときはカン・リーチ不可(リーチは残り4枚以上)。
- **フリテン**: 自分の河に待ち牌がある間はロン不可(ツモは可)。同巡内フリテン(見逃し)は次の自分のツモ・打牌まで。リーチ後の見逃しは以降永続フリテン。
- **CPU自動和了「なし」**: 初期実装では「あり」と同じ挙動とする(仕様が明示的に許容)。
- **後付け「なし」設定**: 完全先付けの厳密な実装は解釈が多岐にわたるため、「待ちのどの牌で和了しても成立する役(ドラ除く)が1つ以上あること」を要求する簡略実装とする。既定値は「あり」。
- **喰いタン「なし」設定**: 断么九を門前限定とする。
- **返し点**: 仕様に順位決定は「持ち点」のみと定義されているため、返し点はウマ・オカを伴わない精算表示(持ち点−返し点)/1000 にのみ使用し、「なし」の場合は精算表示を行わない。順位は常に素点で決定する。
- **同点順位**: 起家に近い方を上位(仕様通り)。起家=対局開始時の東家。
- **複数人間プレイの表示**: 画面下辺は最初の人間席(全席CPUなら東家)の視点で固定する。他の人間席の手牌はその席の手番・応答時のみ公開表示する(ホットシート方式)。
- **CPUの手番遅延**: 進行が視認できるよう、CPU の行動には短い遅延(数百ms)を挟む。テストでは遅延0に設定可能。
- **リーチ宣言牌のロン**: 宣言牌がロンされてもリーチ宣言(供託1000点)は成立扱いとし、和了者が供託を回収する(宣言時に即時減点する仕様と整合させるため)。
- **新ドラ表示牌**: 暗槓・大明槓・加槓のいずれもカン成立(嶺上ツモ)時に即時めくる。
- **結果表示の裏ドラ**: 和了結果の `uraDora` は裏ドラ表示牌を保持し、点数計算へはドラ変換(indicatedDora)済みの値を渡す。
- **暗槓の構成**: 暗槓は赤5を含む同種4枚すべてを槓子にする。ポン・大明槓で手牌から消費する牌は赤5以外を優先する(チーは使用する2枚を明示指定)。
- **喰い替え制限**: 採用しない。
- **同巡フリテン**: 見逃した牌が待ちに含まれる全員に付与し、自分のツモまたは打牌で解消する。一発は自分の次の打牌または任意の副露(暗槓含む)で消える。
- **型配置の補足**: 対局状態の型定義は `src/domains/game/`(純粋な型のみ)、`Rng` 型は `src/types/random.ts` に置き、services が libs を import しない依存方向規約を守る。
