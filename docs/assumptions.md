# docs/assumptions.md — 仕様解釈の判断記録

docs/spec-phase1.md / docs/spec-match-screen.md で未定義・曖昧だった事項に対する判断と根拠を記録する。

## 入出力契約

### A1. hand の牌数(入力例との矛盾)

- **判断**: `hand` は「和了牌を含む純手牌」として `14 − 3×副露数` 枚を正とする。ただし `13 − 3×副露数` 枚で `winTile` が不足している場合は、`winTile` を補完して受理する。
- **根拠**: 仕様本文は「純手牌(和了牌含む)」と明記するが、仕様・受け入れ基準の入力例は 13 枚(`5m` が1枚のみ)であり矛盾する。例を invalid にしないため、両形式を受理する。

### A2. 本場・供託の入力

- **判断**: 入力JSONに任意フィールド `honba`(本場数)・`kyotaku`(供託リーチ棒本数)を追加する。省略時は 0。
- **根拠**: スコープ表に「点数計算(…本場・供託)」とあるが、入力契約に対応フィールドがない。後方互換のため任意フィールドとした。

### A3. payments の形式

- **判断**: `payments` は `{ "from": string, "amount": number }` の配列とする。
  - ロン: `from: "discarder"` の1件(本場加算込み)。
  - ツモ(子): `from: "dealer"` 1件 + `from: "non_dealer"` 2件(各自本場100点込み)。
  - ツモ(親): `from: "non_dealer"` 3件。
  - 供託: `from: "riichi_sticks"` の1件(1000×本数)。供託0本なら出力しない。
  - `total` は payments の合計。
- **根拠**: 仕様は `"payments": [ ... ]` としか定義していないため、支払者区分と金額が機械可読な最小形式を定義した。

### A5. ダブル役満(単体)

- **判断**: 国士無双十三面待ち・四暗刻単騎・純正九蓮宝燈・大四喜は単体でダブル役満とする。役満の複合を含め、合計は**ダブル役満(2倍)でキャップ**する。
- **根拠**: 仕様は「役満の複合: あり(ダブル役満まで)」のみ規定。単体ダブルの扱いは天鳳等の主要ルールに合わせた。

### A6. 役満時の han / fu 出力

- **判断**: 役満は han=13、ダブル役満相当は han=26 として出力し、複合合計も 26 でキャップする。数え役満(通常役+ドラで13翻以上)は実翻数をそのまま出力し、点数のみ役満相当(基本点8000)とする。fu は標準形なら通常の符計算値、七対子形(字一色七対子等)は 25、国士無双は 0 を出力する(役満の点数計算に符は使用しない)。
- **根拠**: 出力契約は `han`/`fu` を数値必須としているため、機械的に一貫する値を定義した。

## ルール解釈

### A7. uraDora の扱い

- **判断**: リーチしていない入力で `uraDora` が指定された場合はエラーにせず**無視**する。
- **根拠**: 仕様の「リーチ時のみ有効」は有効性の規定であり、入力不正の規定ではないと解釈。

### A8. リーチ・一発の前提条件

- **判断**: `riichi` が `none` 以外なのに門前でない(暗槓以外の副露がある)場合、`ippatsu: true` なのに `riichi: "none"` の場合は `invalid_input`。
- **根拠**: 物理的に発生し得ない入力のため。

### A9. situational の整合性検証

- **判断**: 以下に反する入力は `invalid_input` とする。
  - `haitei` ⇒ ツモ / `houtei` ⇒ ロン / `chankan` ⇒ ロン
  - `rinshan` ⇒ ツモかつ槓(kan/ankan)が1つ以上
  - `tenhou` ⇒ 親・ツモ・副露なし・リーチなし・一発なし
  - `chihou` ⇒ 子・ツモ・副露なし・リーチなし・一発なし
- **根拠**: 状況役の定義上あり得ない組合せのため。これ以外の共存(例: haitei と rinshan の同時指定の可否)までは検証しない。

### A10. 赤5の枚数制限と照合

- **判断**: 赤5(`0m/0p/0s`)は各色1枚まで。5の総数は赤を含めて4枚まで。`winTile` や副露牌の照合、ドラ(`dora` 配列)との照合では赤と通常5を同種として扱う。
- **根拠**: 一般的な赤ドラ運用(各色1枚)に従う。

### A11. 連風牌(ダブ東・ダブ南)

- **判断**: 刻子は seat_wind + round_wind の2役(計2翻)。雀頭の符は 2+2=4 符。
- **根拠**: 標準的な運用。符は加算式(連風牌4符)を採用した。

### A12. 喰い平和形の符

- **判断**: 副露ありで符要素がない手(全順子・非役牌雀頭・両面)は、ロン 20符→30符に繰り上げ、ツモは 20+2=22→切り上げ30符。
- **根拠**: 20符はツモ平和のみとする一般的な運用。

### A13. チャンタ・純チャンと混老頭・清老頭の排他

- **判断**: チャンタ/純チャンは順子を1つ以上含む場合のみ成立。全て刻子なら混老頭(+対々和)/清老頭側で扱い、重複計上しない。
- **根拠**: 標準的な役の排他関係。

### A14. 四暗刻のロン完成

- **判断**: ロンで4つ目の刻子が完成する形は明刻扱いで四暗刻不成立(三暗刻+対々和側)。単騎待ちロンは四暗刻単騎。
- **根拠**: 標準ルール。

### A15. 高点法の順序

- **判断**: 総得点(total)最大 → 同点なら han 大 → 同 han なら fu 大、の順で解釈を選択する。
- **根拠**: 仕様の「最も点数が高くなる解釈」を第一基準とし、同点時の決定性を確保するため。

### A16. 七対子の重複対子

- **判断**: 同一牌4枚を2対子として扱うことは不可。
- **根拠**: 標準ルール。

### A17. rules/cli-contract.md の不在

- **判断**: リポジトリに `rules/cli-contract.md` が存在しないため、CLI 契約は docs/spec-phase1.md の入出力JSON契約に従う。
- **根拠**: AGENTS.md の参照先が未作成のため、上位仕様を直接参照した。

## 対戦画面

### A18. 親継続の入力

- **判断**: 和了結果入力の「親継続」は、点数反映仕様(親和了=連荘・本場+1、子和了=次局・親移動・本場0)から自動決定される値を表示するフィールドとする(ユーザー編集不可)。
- **根拠**: 任意編集可能にすると点数反映仕様の規則と矛盾し得るため。編集可能な連荘判定は流局処理(将来フェーズ)で扱う。

### A19. 対戦中の補助表示の初期値

- **判断**: 牌山生成・配牌・手牌操作はスコープ外のため、補助表示は開始状態の静的な値(残り山70枚、ドラ表示牌1枚、捨て牌河は空、鳴きなし、リーチなし、手番は親、アクションは打牌のみ有効)を表示する。
- **根拠**: 仕様は表示項目のみ規定しており、進行ロジックは「含まない」に明記されているため。

### A20. 画面からの点数計算

- **判断**: 和了結果入力の翻数・符から支払い内訳を求める計算は、エンジンの `Score` ドメイン公開API(`@/domains/score`)を経由する。供託・本場の加算、親子・ツモロン別の点数もすべて同APIで計算し、画面側では再実装しない。
- **根拠**: 「画面は点数計算エンジンのドメインロジックを重複実装しない」要件。

### A21. 局の進行と終局

- **判断**: 子和了時の局進行は 東1→東2→東3→東4→南1→…(半荘戦は南4まで、東風戦は東4まで)とし、最終局で子が和了した場合も局表示はそのまま(終局判定・順位計算は将来フェーズ)。
- **根拠**: ゲーム進行・流局処理はスコープ外のため、点数反映仕様に必要な最小限の進行のみ実装。

### A22. プロジェクト構造

- **判断**: rules/architecture.md の構造(`src/app/` ほか)に合わせ、Next.js の `app/` を `src/app/` へ移動し、パスエイリアス `@/*` を `./src/*` に変更した。また、CLI(Node 直接実行)と Next.js の両方から同一ソースを使うため、`src/domains` / `src/services` / `src/cli` 内の相対 import には `.ts` 拡張子を付与し、tsconfig に `allowImportingTsExtensions` を追加した。
- **根拠**: 規約のフォルダ構造が `src/` 前提であること、Node の type stripping 実行(`pnpm calc`)が拡張子付き相対 import を要求すること。

### A23. 入力JSONの省略可能フィールド

- **判断**: `hand` / `winTile` / `winType` / `seatWind` / `roundWind` は必須。`melds`(既定 `[]`)、`dora`(`[]`)、`uraDora`(`[]`)、`riichi`(`"none"`)、`ippatsu`(`false`)、`situational`(`[]`)、`honba`(`0`)、`kyotaku`(`0`)は省略可能とし、存在する場合は型を検証する(型不正は `invalid_input`)。
- **根拠**: 仕様の入力例は全フィールドを含むが必須/任意の規定がないため、意味的に省略が自然なフィールドに既定値を与えた。

### A24. プレイヤー設定の初期値

- **判断**: 1席目(東家)=人間、2〜4席目=CPU(レベル: 標準)、表示名は「プレイヤー1〜4」。CPUレベルの選択肢は操作種別が CPU の席のみ表示する。
- **根拠**: 仕様は項目のみで初期値未定義。一般的な麻雀アプリの慣習に従った。仕様の「CPUの場合のみ選択する」に基づき人間の席では非表示。

### A25. 和了結果入力の翻数・符の入力形式

- **判断**: 翻数は 1〜13翻、符は 20/25/30〜110符 の選択式とする。13翻はエンジン側で数え役満として扱われる。
- **根拠**: 自由入力による不正値(0翻・7符など)を構造的に排除するため。

### A26. 放銃者の選択制約

- **判断**: 放銃者の選択肢から和了者を除外する。和了者の変更で衝突した場合は次の席へ自動振り直し。ツモ時は放銃者を無効化する。
- **根拠**: 和了者=放銃者という不正入力を UI 上で排除するため。

### A27. 最終局での子和了

- **判断**: 最終局(東風戦=東4局、半荘戦=南4局)で子が和了した場合、局表示は据え置きつつ、親移動と本場0リセットは点数反映仕様の通り適用する。
- **根拠**: 終局判定・順位計算は将来フェーズ(A21)のため、表示の矛盾を最小化する挙動とした。
