# assumptions.md

本書は仕様の曖昧点に対する判断と根拠の記録である。各項目は「判断」と「根拠(仕様・設計契約書のどこが曖昧か)」をセットで記載する。実装上の技術的な回避策など、仕様解釈に直接関わらない事項は末尾の「その他実装上の判断」にまとめる。

## 点数計算

### 牌・手牌分解(domains/tile, meld, hand)

- **`Tile.nextInSeries` は常に `red: false` を返す。** 設計契約書は `fromIndex34` について「red は常に false」と明記するが `nextInSeries`(ドラ表示牌→ドラの算出)には明記がない。ドラは牌の「種類」で決まり、赤ドラの red フラグは物理的な牌の属性であって次牌の種類算出には無関係なため、`fromIndex34` と同様に常に `red: false` とした。
- **`StandardDecomposition.blocks` の並び順は「副露ブロックを `melds` の順、続けて手牌由来ブロックを34種インデックス昇順」とする。** 契約書は4要素タプルであることのみを規定し順序を規定していないための独自ルール。和了牌は必ず concealed 側に含まれるため `winBlockIndex` が副露ブロックを指すことはない。
- **面子構成(パーティション)が同一でも和了牌の役割(待ちの種類)が変わる場合は別の `StandardDecomposition` として列挙する。** 例: `3m4m4m5m5m6m` で和了牌が `4m` のとき、嵌張/両面のどちらの役割とも解釈できる。契約書 §4 の指示(全解釈を列挙)に従った。面子分解自体は決定的アルゴリズム(残り牌の最小indexから処理)で一意になるため、パーティションの重複は生じない。

### 役判定(domains/yaku)

- **上位役成立時は下位役を出さない。** junchan/honroutou 成立時は chanta を、chinitsu 成立時は honitsu を、ryanpeiko 成立時は iipeiko を出さない。契約書の役名一覧(§7)は包含関係を暗示するのみで排他の明記がないため、実装で明示的に排他とした。
- **double_riichi 成立時は riichi を併記しない。** 2翻の単独役として扱う(契約書は riichi/double_riichi が「排他」とのみ記すため、"douhle_riichi 一本のみ計上"と解釈)。
- **連風牌(場風=自風)の刻子は seat_wind と round_wind を別役として両方計上する(計2翻)。** 契約書 §7 に「連風牌は seat_wind と round_wind 両方成立」と明記されている前提を実装側でも踏襲・徹底した。
- **排他役の扱い:** 四暗刻と四暗刻単騎、国士無双と国士無双十三面、九蓮宝燈と純正九蓮宝燈はそれぞれ上位のみを採用する(契約書の役満名一覧にランク違いとして併記されているのみで排他規定が明記されていないための実装判断)。
- **ロンの双碰(シャンポン)和了で完成した刻子は明刻扱い(手牌分解の `open:true`)とするため、四暗刻にはならず三暗刻+対々和となる。** 契約書 §4「ロンの shanpon 和了刻子は Block.open=true」を、四暗刻不成立という標準ルール的帰結として明示した。
- **九蓮宝燈の判定は面子分解の解釈によらず、門前手牌全体(1112345678999+X の形)で行う。** 純正(9面待ち)は和了牌を除いた13枚が `1112345678999` のときとした。契約書はアルゴリズムを規定していないため、面子分解に依存しない判定方式を採用した。
- **緑一色は發を含まなくても成立する。** 仕様の確定事項として実装。
- **ドラ(dora/ura_dora/aka_dora)は役判定層(yaku)では扱わず、点数計算ファサード(domains/scoring)で計上する。** 契約書 §5 の `Yaku.detect` シグネチャに「ドラは含めない」と明記されている方針を踏襲。
- **役満成立時は通常役を計上しない。** 呼び出し側(scoring 層)の責務として整理(契約書 §5 に同様の記載あり)。

### 符計算(domains/fu)

- **明刻/暗刻・明槓/暗槓の判定は `Block.open` のみを使用し、`meldType` は参照しない。** `Block` 型には `open`(Meld.isOpen 由来)と `meldType`(null=手牌構成)の2フィールドがあるが、ロンの双碰完成刻子のように「副露ではないが `open:true`」というケースが存在する。契約書 §5「ロンの shanpon 完成刻子は明刻扱い」を満たすため `open` のみを判定基準に統一した(ポン由来の明刻とロン双碰の明刻を同一ロジックで扱える)。
- **喰い平和形(20符)への繰り上げ判定は「非門前かつ丸め後20符」の条件のみで行う。** 契約書は「鳴きあり手が20符になった場合はロン・ツモとも30符に繰り上げ」とのみ規定し、形状条件(全順子・非役牌雀頭・両面待ち)までは明記していない。非門前手の符内訳(基礎20+ツモ2+待ち符+雀頭符+面子符、門前ロン加符は非門前なので常に0)がすべて0のときに限り合計20になるため、この条件は数学的に「食い平和形」以外の非門前手を誤検出しないことと等価であり、`opts.isPinfu` を条件に含めず丸め後の値のみで判定する実装とした。

### 点数計算(domains/score)

- **`yakumanMultiplier` は下限0にもクランプする(`Math.min(Math.max(multiplier, 0), 2)`)。** 契約書は上限2のみ規定し下限は明記していないが、呼び出し側の入力を信頼しすぎない防御的実装としてを下限0も設けた。0以上の通常入力の挙動は契約と完全一致する。

### 高点法・JSON契約・CLI(domains/scoring, services/score-calculator, cli)

- **`dora`/`uraDora` 配列は各エントリごとに独立して一致数を数えて合計する。** 契約書は各ドラ表示牌についての一致数合計とのみ規定し、配列内に同一牌が複数回現れた場合を明示していない。カンが重なった場合など実際のドラ表示牌が複数枚になり得るルールと整合する挙動として採用した。
- **役満経路ではドラ(dora/ura_dora/aka_dora)を一切加算しない。** 契約書 §6 の役満経路の記述にドラ加算の言及がないため、実際の麻雀ルール(役満にドラは乗らない)に倣った。
- **役満の `yaku` エントリの `han` は個別に `13×rank` を表示し、`ScoreResult.han`(全体の翻数)は `13×min(Σrank, 2)` とする。** 契約書の規定をそのまま実装(複数役満複合で Σrank が2を超えても全体は上限2倍相当に留める)。
- **役満経路の `isPinfu` は常に `false` として `Fu.calculate` に渡す。** 役満を構成する Decomposition は構造上 pinfu の形状と両立しないための実装判断。
- **`services/score-calculator` の入力検証範囲(契約書 §6 の invalid_input 条件に追加した独自判断):**
  - `honba`/`kyotaku` は指定時、0以上の整数であることを要求する(負数・小数は invalid)。
  - `rules` オブジェクトは存在時のみ検証し、`kuitan`/`redDora` 以外の余分なプロパティは無視する(将来のルール追加を想定)。
  - 副露(`melds`)の牌構成検証は `Meld.isValid` にすべて委譲する。
  - 同種牌4枚上限・赤5重複チェックは `hand`(正規化した純手牌)と `melds` の牌のみを対象とし、`dora`/`uraDora` フィールドの牌(表示牌が示す値であり実際の保持牌ではない)は対象外とする。
- **`winTile` の (a)ケース(hand長=14−3×melds数)含有チェックは `Tile.strictEquals`(赤5を区別する厳密一致)で行う。** 契約書は「winTile が hand に含まれていること」とのみ規定しており、`winTile` は特定の1枚を指す入力値であるため厳密一致を採用した。
- **tenhou/chihou の入力検証は以下を invalid_input とする:** `situational` に tenhou/chihou を含むのに `melds` が非空(絶対門前のため)/ tenhou かつ `seatWind !== "ton"`(天和は親のみ)/ chihou かつ `seatWind === "ton"`(地和は子のみ)。契約書は「席矛盾・副露併存」とだけ列挙しており、具体条件を独自に定めた。

## ゲーム進行

- **`domains/game` と `services/game-engine` の役割分担:** `domains/game` には MatchState/GameView/GameAction/LegalAction 等の型定義と、牌山構築・配牌(Wall/Deal)・座席演算(Seat)・決定的PRNG(Prng)という「単一状態オブジェクトの構築・pure query」のみを置く。ツモ→打牌→鳴き→和了/流局という複数ドメイン(hand・meld・scoring・win-context)を組み合わせる進行ロジックは `services/game-engine` に実装した。architecture.md の「複数ドメインを組み合わせるロジックは services/」という基準に従い、これにより `services/cpu-ai` は `services/game-engine` を import せず `domains/game` の型のみに依存でき、「services 間の import 禁止」を満たす。
- **決定的な牌山コンストラクタは `domains/game/deal.ts` の `Deal.deal`。** 136枚の牌山配列(並び順確定済み)を受け取り配牌・王牌確保・ドラ表示牌めくり・親の第一ツモまでを行う正式なドメイン生成関数であり、`GameEngine.createMatch` 自身もこれを内部で使う。テストはこの関数に任意の並び順の牌山を渡すことで配牌・ツモ順を完全に制御する。
- **`apply` を純粋関数に保つため、`MatchState` に関数ではなく plain number の `rngSeed` を持たせる。** 契約の `apply(state, action): MatchState` は Rng を引数に取らないが、局が進んで次局の牌山シャッフルに乱数が必要になる。`domains/game/prng.ts` の mulberry32 による決定的ステップ関数で解決し、`createMatch` が注入された `Rng` を1回だけ呼んで初期シードを作る以外は `Math.random` を一切使わずに何局でも進行できる(`Math.random` を直接使うのは `src/libs/random.ts` の `createRandomRng` のみ)。
- **配牌の分配順序は `wall[0,52)` を起家から seat0,1,2,3 の順に13枚ずつという単純な連続ブロックとした。** 実際の配牌(4-4-4-1×4+1枚ずつ)の物理的順序は再現していないが、牌山配列は既にシャッフル済みのため手牌分布に偏りは生じない。
- **`GameEngine.createMatch` は「親の第一ツモ完了状態」を返すため、配牌直後に観測できる残り山は69枚(70−1)になる。** 契約が createMatch を「配牌済み・親の第1ツモ完了状態まで進める」と明記していることの帰結。
- **天和・地和の判定は `hasDrawnThisKyoku`(打牌/カンの意思決定完了で true)と `anyCallHappened`(ポン・チー・加槓・大明槓の成立で true。暗槓は含めない)で行う。** `!hasDrawnThisKyoku && !anyCallHappened` で「先行する鳴きが無い最初のツモ」を座席によらず統一的に判定する。暗槓は他家の牌を使わず面前を崩さないため天和・地和判定を妨げないという一般的解釈を採用したが、一発判定用の `ippatsuEligible` は暗槓を含む全カンの成立時に解除する(一発は暗槓でも崩れるという一般的解釈)。
- **一発の管理:** リーチ宣言と同時に宣言者の `ippatsuEligible` を true にし、(a) 誰かが鳴き(ポン/チー/暗槓含む全カン)を成立させた時点で全席解除、(b) リーチ者自身が次の打牌を行った時点で当該席のみ解除、の2経路のみで解除する。
- **フリテンの管理:** 動的判定(ロン宣言可否のたび `Hand.waitingTiles` を計算し自分の河全履歴と突合せ)、一時フリテン(claims フェーズでロン非成立時、ロンの合法手を提示されパスした席に付与し、次の自分のツモでクリア)、永続フリテン(同じ場面で既にリーチ済みの席は局終了まで解除しない)を実装。頭ハネで敗れた席にはフリテンを課さない(ロン宣言自体は見逃しではないため)。
- **リーチ可能条件の「残り山4枚以上」はツモ後の残り枚数(`Wall.remaining(state)`)で判定する。** 契約はツモ前/後いずれの残り枚数か明示していないため、プレイヤーが合法手を評価する時点の状態(ツモ後)を採用した。
- **ポン・チー・カン(大明槓)で手牌のどのインスタンスを面子に使うかは点数計算に影響しない。** `Scoring.calculate` のドラ集計は手牌+副露の全物理牌合計に対して行うため、赤牌がどちら側に残るかで点数は変わらない。実装では「赤でない牌を先に面子へ回す」という表示上一貫したルールを採用した。
- **副露された牌も打牌者の河から取り除かず、そのまま表示し続ける。** `RiverTile` は「その席が実際に打牌した履歴」を保持する設計とし、フリテン判定にもこのまま使う。
- **チャンカンは加槓のみを対象とする(暗槓・大明槓は槍槓の対象外)。** 加槓宣言時は即座に成立させず `ClaimsPhase(kind:"chankan")` へ遷移して他家のロンのみを募り、誰もロンしなければ成立させる。契約 §9 の既定事項どおり。
- **連荘・輪荘・終局判定:** 親の和了は本場+1・供託回収・親継続。子の和了は本場0リセット・供託回収・親交代(下家へ)。荒牌流局は本場+1(連荘/輪荘いずれも)・供託は次局へ持ち越し、親テンパイなら連荘、ノーテンなら親交代。オーラスは親が連荘条件を満たす限り継続(アガリやめ・テンパイやめは実装しない)。トビ(いずれかの持ち点が0点未満)は連荘判定より常に優先して即座に終局。終局時の順位は持ち点降順、同点は seat index 昇順(起家に近いほう)で決定し、残存供託はトップの持ち点に加算してから順位付けする。
- **後付け(`atozuke`)・喰い替え制限は実装していない。** `RuleSet.atozuke` は保持のみで、「なし」設定時の制限(役確定まで鳴き不可等)はゲーム進行エンジン側で行わない。喰い替え制限も同様(契約 §9「喰い替え制限なし」を踏襲)。

## CPU AI

- **全レベル共通の基本方針:** ツモ/ロンが合法手にあれば必ず宣言する。暗槓・加槓・大明槓は自分から選択することはない(合法手にあっても行わない)。`docs/spec-phase1.md` のレベル別要件表はどのレベルにも「カンを行う」という記載が無いため、レベルを問わず統一した。`RuleSet.cpuAutoWin` は `GameView` に転写されず CPU からは参照できないため、仕様書の「なし設定でも同じ挙動を許容し assumptions に記録する」旨に従い、ツモ/ロンが合法手にあれば設定に関わらず必ず宣言する(常に「あり」相当として実装)。
- **入門(beginner)レベル:** 次にリーチが合法手にあれば宣言する(候補打牌の先頭を選ぶ)。それ以外は打牌候補ごとに「切った後のシャンテン数」を `Hand.shanten` で評価し最小の牌を選ぶ(同シャンテンなら字牌→老頭牌→それ以外の優先順)。ポン/チー/大明槓の claims はすべてパスする(鳴きを一切行わない)。
- **標準/上級レベルの鳴き判定に必要な「対象牌」の推定(`guessClaimTile`):** `GameView`/`LegalAction` は claims フェーズの対象牌(誰が何を捨てたか)を直接公開していないため、以下の優先順位で推定する。(1) `chi` が合法手にあれば上家の河の最後の1枚で確定、(2) `kan`(大明槓、`tiles.length===1`)ならその1枚で確定、(3) `pon` のみなら自分以外の3席を下家→対面→上家の順に見て自手牌にその席の河の最後の牌と同種が2枚以上あればそれとみなす(推定であり複数の対子を同時に持つ場合に稀に誤り得るが、実際に選択する `GameAction` は対象牌を含まないためゲーム進行自体は壊れない)。特定できない場合は鳴かない(保守的に倒す設計)。
- **鳴いて役が確保できるかの判定基準(標準/上級共通):** 呼ぶ牌(またはチーで完成する面子の構成牌)が役牌である/既に役牌の明刻を副露済みである/鳴いた後の手牌全体が么九牌を含まない(タンヤオ確定形)、のいずれかを満たせば「役が確保できる」とみなす。加えて「鳴いた後にシャンテンが厳密に進む場合のみ」を要求する(同シャンテンなら鳴かない)。
- **標準の押し引き(現物優先)は「複数のリーチ者全員に対して現物」であることを要求する。** ある牌が一方のリーチ者には現物でも他方には現物でない場合、標準レベルは安全とみなさない。現物候補が無ければ通常の効率打牌に戻る。
- **上級の危険牌評価は4段階の簡略ヒューリスティックとする:** 0. 現物、1. 3枚以上見えている字牌(残り1枚以下)、2. スジ(同色±3の数牌、両面待ちのみ有効)、3. 老頭牌・未分類の字牌、4. それ以外の中張牌(最も危険)。複数リーチ者がいる場合は各リーチ者に対する危険度の最大値を採用する。壁読み・またぎスジ・一盃口/対子絡み等の高度な読みは実装していない(仕様は「スジ・現物・字牌の安全度」とのみ要求)。
- **上級の押し/降りは「2シャンテン以上か否か」の二値で切り替える。** 仕様表は1シャンテンの扱いを明記していないため、1シャンテンもテンパイと同様に「押し」側として扱う(2シャンテン以上でのみ安全牌優先に切り替え、危険度が同点の場合のみ `Tile.compare` でタイブレーク)。押し側では危険度を一切考慮しない。
- **リーチ可否(標準/上級共通)の「待ち枚数」「打点向上」の定義:** 待ち枚数は `Hand.waitingTiles` の各待ち牌について見えている枚数を4から引いた残り枚数の合計とし、2枚以上ならリーチ。打点向上は打牌後の手牌にドラ(表ドラ・赤ドラ)が1枚でも残っていればリーチする(裏ドラは非公開情報のため考慮しない)。リーチ候補の中からまず待ち枚数最大の1枚を選び、その1枚について上記条件で判定する。
- **打牌選択の「受け入れ枚数」は自分の手牌(ツモ牌含む)も見えている牌として数える。** 仕様表は自分の手牌を明記していないが、自分自身は当然把握しているため `computeVisibleCounts` は自手牌・全員の副露(暗槓のタイル構成含む)・全員の河・ドラ表示牌をすべて含めて残り枚数を数える。
- **rng の使用箇所は決定的タイブレークで解決できない異常系フォールバックのみ。** 各レベルの意思決定は GameView の情報のみから決定的に導出され、同点候補のタイブレークは `Tile.compare` による決定的順序で行う。rng を実際に消費するのは想定外の LegalAction しか無いフォールバック(`convertFallback`)のみ。

## 対戦画面

- **CPU の自動進行は `GameEngine.legalActions` から「次に決定すべきCPU席」を導出する。** `MatchState.phase` の内部構造(actor/eligible/responses 等)を feature 側で直接読んで手番を再実装するのではなく、`legalActions(state)` が返す「今応答すべき席の合法手一覧」から `config.players[seat].kind === "cpu"` な最初のエントリを使う(`utils/pending-actor.ts`)。turn フェーズでは常に1件、claims フェーズでは未応答の eligible 席の分だけ候補が並ぶため、Phase の内部形状に依存せず turn/claims 両方で機能する。claims フェーズで人間とCPUの両方が応答待ちの場合、CPU側の決定は人間の応答を待たずに独立にスケジュールされる(`applyClaimAction` は席ごとに独立受理され全員そろった時点でのみ解決されるため、応答順は合否に影響しない)。
- **結果ダイアログ表示時点で持ち点は更新済みであり、「確定」は次局への進行操作である。** 判断: `GameEngine` は局終了時点で点数計算(`Scoring.calculate` の結果)を `MatchState` に適用済みであり、結果ダイアログはその適用結果を表示しているに過ぎない。UI上の「確定」ボタンは `confirm` アクション(次局へ進む、またはオーラスなら終局へ進む)をトリガーするものであり、点数反映そのもののトリガーではない。全席CPU設定であっても `confirm` は自動発火させず常に手動ボタンとした(CPUの自動進行は turn/claims フェーズのみが対象)。根拠: spec-match-screen.md は「『確定』ボタンで点数反映し次局へ進む」と記載しているが、これは表示上の体験(結果を確認してから進む)を説明したものであり、実際の点数計算タイミング(局終了時にエンジンが計算・適用)とは別の話であるため、実装では「点数は局終了時に反映済み・確定は進行操作」という解釈で整理した。
- **返し点(`returnPoints`)は設定として保持するが、最終順位は持ち点のみで決定する。** 判断: `RuleSet.returnPoints`(ウマ・オカの基準点)は `MatchConfig`/`RuleSet` に保持し設定画面にも表示するが、対局終了時の順位計算(ランキング画面)では使用せず、各席の持ち点(供託回収後)の降順のみで順位を決定する。根拠: spec-match-screen.md・spec-phase1.md のいずれにも返し点を用いたウマ・オカの具体的な計算式(点差の配分方法)の規定がなく、「持ち点降順で順位を決定する」という記述のみが根拠として存在するため、返し点は設定値の受け皿として実装し、順位計算そのものへの適用は行わないこととした。
- **対戦開始設定の既定値:** 表示名の既定は人間席「あなた」、CPU席「CPU1」〜「CPU3」(座席順)。CPUレベルの既定値は spec に明記がないため「標準」とした(入門/標準/上級の中間であり "通常対戦向け" という説明とも整合するため)。席の操作種別を人間→CPUに切り替えた際、直前のCPUレベルがあればそれを保持し、無ければ既定値「標準」を設定する(CPU→人間に戻すと `cpuLevel: null` に戻す)。
- **複数の人間席を想定した設計とした(既定は席0のみ人間)。** `PlayerConfig` は4席それぞれ独立に `kind` を設定できるため、`MatchView` は「人間として設定されている席」をすべて列挙し、それぞれに `HandPanel` を描画する(既定構成では席0のみ表示)。将来ローカル対戦(同一画面での複数人間プレイ)を設定した場合も、各人間席は自分の手番/応答可能なときにのみ操作ボタンが有効になる。仕様は単一人間プレイヤーのみを前提とした記述だが、拡張性を考慮しこの設計とした。
- **牌の表示形式は `Tile.format` の内部表記をそのまま出さず、日本語表記(例: "1萬", "5筒(赤)", "東")に変換する表示専用ユーティリティ(`features/match/utils/tile-display.ts`)を設けた。** 赤ドラは牌ラベルに "(赤)" を付け文字色でも強調する(design-contract で明示的に許容されている表示変換)。
- **役名の表示ラベルは `features/match/utils/yaku-labels.ts` に日本語変換テーブルを持たせた。** `ScoreResult.yaku` は英語スネークケース(design-contract §7 確定名一覧)で返るため、ドラ(dora/ura_dora/aka_dora)も含め日本語ラベルへ変換する。未知の役名(将来追加された場合)はそのまま表示するフォールバックとした。

## その他実装上の判断

以下は仕様解釈というより実装技術上の判断・回避策・既知の制約であり、参考として記録する。

- **シャンテン計算アルゴリズム:** 34種カウント配列に対する再帰探索(各indexについて刻子/順子/対子/塔子として使う/使わないを全探索し `melds+taatsu<=4` を上限に `8-2*melds-min(taatsu,4-melds)-(hasPair?1:0)` を最小化)をメモ化(index・melds・taatsu・hasPair・残りcountsをキー)して実装した。七対子・国士無双は標準formulaで別途計算し `meldCount===0` のときのみ通常形と比較する。
- **CLIテスト(`src/cli/__tests__/calc.cli.test.ts`)における `import.meta.url` 解決の回避策:** `vite.config.ts` の `test.environment` が `"jsdom"` のため、グローバルの `URL` コンストラクタで `new URL("../calc.ts", import.meta.url)` を解決すると jsdom 提供のグローバル `URL` が `import.meta.url` を無視し誤った URL(`http://localhost:3000/...`)を返す。そのため `fileURLToPath(import.meta.url)` で自ファイルパスを取得し `node:path` で `calc.ts` への相対パスを組み立てる方式とした。
- **CPU AI のパフォーマンス最適化(`Hand.shanten` 呼び出し回数の削減):** 打牌候補×34種を毎回フルスキャンすると `decide` 1回が数百msに達するケースがあったため、`discard-policy.ts` の `evaluateDiscardCandidates` は (1) 各候補の「切った後のシャンテン数」のみをまず求め、(2) 最小シャンテンの候補についてのみ34種の受け入れ枚数スキャンを行い、(3) 呼び出し内でのみ牌の多重集合キーによるローカルメモ化を行う、という2段階の絞り込みで呼び出し回数を削減した。この最適化後、標準/上級4人 CPU の東風戦自動進行テストは概ね10〜15秒で完走する(最適化前は30〜75秒)。
- **対戦画面(`features/match`)は表示専用ユーティリティ層を設け、ドメイン計算を feature 側で再実装しない設計とした。** `utils/`(牌の日本語表記・役名ラベル・席の風表示・既定設定・次CPU席検出・CPU思考待ち時間)はいずれも `GameEngine`/`domains` の公開APIが返す値をそのまま読むだけであり、和了判定・点数計算・合法手判定などのドメイン計算は一切実装していない。
- **`useMatch` の rng/scheduler の保持は `useRef` ではなく `useState` の遅延初期化(`useState(() => ...)`)を使った。** 当初は「render中に1回だけ作って以後固定する値」として `useRef` の遅延初期化を検討したが、本リポジトリの ESLint 設定(`react-hooks/refs`, React Compiler対応版)が render 中の ref 読み取りを一律エラーにし(`eslint-disable` は規約で禁止)、rules/hooks.md の判断基準(「render で読むなら useState」)にも合致するため `useState` の遅延初期化に統一した。挙動は変わらず1回だけ生成され以後同一インスタンスを指す。
- **テストでのフェイク注入:** `MatchScreen`/`MatchView` に `rng?`/`scheduler?`/`initialMatch?` の3つのオプションpropsを追加し、テスト側から固定seedのPRNG・手動flush式のフェイクスケジューラ・`Deal.deal`で構築した任意局面を注入できるようにした(本番の `app/page.tsx` は `<MatchScreen />` のみを呼び、これらは渡さない)。`GameEngine`/`CpuAi` はモックせず実物のまま、対戦開始→和了→確定→次局という一連の流れをコンポーネントツリーごしに検証する。
- **既知のテスト不安定性:** `src/services/cpu-ai/__tests__/cpu-ai.integration.test.ts` の標準レベル4人自動進行テストは、標準レベルのシミュレーションのみで38〜48秒かかるため、フルスイート実行時の並列負荷次第ではデフォルト60秒タイムアウトに達して失敗することがある(単独実行や再実行では成功する)。実装のバグではなくテスト実行環境の負荷起因の遅さと考えられる。Wave6 のフルスイート実行結果は本ドキュメントとは別に検証レポートに記録する。
