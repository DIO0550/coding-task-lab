# テスト規約

**基本方針: 古典学派(Classicist / Detroit School)でテストを書く。** 詳細は「古典学派のテスト」セクションを参照。

## 配置と命名

モジュールフォルダは `index.ts` を公開APIとし、テストは同フォルダ内の `__tests__/` に置く。

**基本形: 1フォルダ = 1実装ファイル + `__tests__/`。** この形を必ず守ること。

```
<モジュールフォルダ>/
  index.ts                          # 公開API(外部はここからのみ import する)
  <実装ファイル>.ts                  # 実装ファイルは1フォルダにつき1つ
  __tests__/
    <テスト対象ファイル>.<カテゴリ>.test.ts
```

- 実装ファイルが2つ以上必要になったらサブフォルダに分割し、各サブフォルダでも同じ形(1実装ファイル + `__tests__/`)を保つ

命名規則: `{テスト対象ファイル}.{カテゴリ}.test.ts`

- カテゴリはテストの観点を表すラベル。例:
  - `score.normal.test.ts` — 正常系
  - `score.edge.test.ts` — 境界値・異常系
  - `score.yakuman.test.ts` — 特定の仕様領域
- **describe のネストの代わりにカテゴリ(=ファイル)で分割する**。1ファイルが肥大化したらカテゴリを分けること

## 古典学派のテスト

古典学派の2本柱は「**何をテストするか = 振る舞い**」と「**依存をどう扱うか = 実物を使う**」。両方を必ず守ること。

### 1. 振る舞い(仕様)をテストする

テストは**外から観測できる振る舞い**に対して書く。実装の内部構造に対して書かない。

- テスト対象は公開API(`index.ts` の export)の「入力 → 出力/最終状態」のみ。内部のヘルパー関数・中間データ構造・処理順序はテストしない
- テスト名は**仕様の文として**書く(「○○のとき□□になる」)。関数名・実装語彙ではなくドメイン語彙を使う
  - OK: `"門前ツモのみの手は20符2翻として計算される"`
  - NG: `"calculateFu が 20 を返す"`、`"parseHand が内部で sortTiles を呼ぶ"`
- 1テスト1振る舞い。複数の仕様を1つのテストで検証しない
- **リファクタリング耐性を判断基準にする**: 振る舞いを変えずに実装を書き換えたときに壊れるテストは、実装詳細をテストしている証拠なので書き直す
- テストケースの根拠は仕様(docs/spec-phase1.md)に求める。仕様にない振る舞いをテストで固定しない(実装の偶然の挙動を仕様化しない)
- **API を作り替えるときは、既存テストの観点を先に数える。** 型名やメソッド名を変えると既存のテストファイルが丸ごと動かなくなるが、そこにある観点(境界値・異常系・複合・空など)は仕様であって、書き換えの都合で消えてよいものではない。**新しく思いついたケースだけを並べた一覧は、たいてい元より薄い**

### assert は「落ちうるか」と「1つの仕様か」で見る

テスト名が仕様の文になっていても、assert がその仕様を捉えていないことがある。書いたあとに次の2つを確かめる。

**1. その assert は落ちうるか。** 入力にその情報が存在しない状態で「出ない」ことを確かめても、実装が何をしても通る。

判断の仕方: **その assert を通すために実装をどう壊せるかを考える。** 壊し方が思いつかないなら、そのテストは何も守っていない。

- **既定値・フォールバックがある処理では、既定値と違う答えになる入力を選ぶ。** 規則で決まる答えと既定値が同じ入力では、規則を丸ごと壊しても既定値のほうで通る(符の切り上げを確かめるのに、切り上げ前から 10 の倍数になる手を選ばない)
- **「空になる」「出さない」を確かめるときは、対照を1件置き、入力から自明にならない側を見る。** 0 件のときに行が無いのは入力から決まるので、行の数では実装を守れない。守りたいのが「0 件なら枠を出さない」なら枠そのものを見る
- **`queryBy*` が `null` になる理由が2通り以上あるなら、その assert は守っていない。** 対象を `getBy*` で引いてから、外れてほしい側だけを見る
- **落ちるか迷ったら、その1件だけ実装を壊して走らせる。** 頭で判断せず確かめる

**2. 1つの assert が複数の仕様を固定していないか。** 表示全体を文字列として比べると、テスト名が指していない仕様まで巻き込む。関係のない変更で落ちるため、リファクタリング耐性が下がる。

### 2. モックは原則使わない

依存は実物を使い、相互作用(呼び出し回数・引数)ではなく**結果の状態・戻り値を検証**する。

- `domains/` `services/` のテストでモック・スタブ・スパイの使用は**全面禁止**(純粋関数なので実物で検証できるはず。モックが必要に感じたら設計を見直す)
- features / hooks / components のテストでも、`domains/` `services/` は必ず実物を使う(ドメインロジックのモック化は禁止)
- 例外として代替してよいのは**プロセス外・制御不能な境界のみ**: `libs/` が包む外部I/O(localStorage、fetch、時刻、乱数)。この場合もモックライブラリによる自動モックより、テスト用の単純な実装(フェイク)を優先する
- `vi.mock` によるモジュール丸ごと差し替えは禁止
- 内部実装の呼び出し検証(`toHaveBeenCalledWith` 等)は外部境界の検証以外で使用しない

```typescript
// NG: ドメインロジックをモックして相互作用を検証
vi.mock("@/services/score");
test("...", () => {
  render(<ScoreView />);
  expect(ScoreService.calculate).toHaveBeenCalledWith(/* ... */);
});

// OK: 実物を通して最終的な出力を検証
test("平和ツモの手で 1300/700 と表示される", () => {
  render(<ScoreView hand={setupHand({ /* ... */ })} />);
  expect(screen.getByText("1300 / 700")).toBeInTheDocument();
});
```

## テストの書き方: ネスト禁止

Kent C. Dodds の "Avoid Nesting when you're Testing" に従う。

- `describe` のネストは禁止(ファイル直下に `test` / `it` をフラットに並べる。グルーピングが必要ならカテゴリファイルを分ける)
- `beforeEach` での変数共有・ミューテーションは禁止。テストに必要なセットアップは**各テスト内に書く**か、セットアップ関数(例: `setup()`, ファクトリ)を呼び出す
- テストは1つだけ読めば前提がすべて分かる状態にする(他のテストや上方のフックを読まないと理解できないテストは書かない)

```typescript
// NG
describe("Score", () => {
  let hand: Hand;
  beforeEach(() => {
    hand = createHand(/* ... */);
  });
  describe("when tsumo", () => {
    it("...", () => { /* hand がどこで何になっているか追えない */ });
  });
});

// OK: __tests__/score.normal.test.ts
test("平和ツモは20符になる", () => {
  const hand = setupHand({ /* このテストに必要な状態を明示 */ });
  expect(Score.calculateFu(hand)).toBe(20);
});
```

- クリーンアップが必要な場合のみ `afterEach` を許可(リソース解放など、テストの理解に影響しないもの)

## テスト用ヘルパーの置き場所

**テストに書こうとしているヘルパーが汎用の操作なら、それは実装側に足りていない機能。** テストファイルにその場しのぎで書かず、`utils/` やコンパニオンオブジェクトへ実装する。

- 判断軸: そのヘルパーは**テストであることに依存しているか**。`expect` を含む表明はテスト固有だが、「`Ok` から値を取り出す」「オブジェクトを組み立てる」は汎用操作なので実装側に置く
- **移す前に、その assert がそのヘルパーを必要としていること自体を疑う。** ヘルパーが表示のための綴りを組み立てているなら、実装側へ移すと表示の知識がドメインへ入る。多くの場合テストが見たいのは綴りではなく**構造**で、構造のまま比べればヘルパーごと要らなくなる
- 同じヘルパーを2つ以上のテストファイルに書いたら、その時点で共通化する(実装側へ移せるならそちらを優先)
- テスト固有のセットアップ(ファクトリ・`setup()`)は各テストから呼ぶ形で共有してよい
