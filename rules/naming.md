# 命名規約

## 名前と実体を一致させる

**名前が約束することと、実際にやること・返すものを一致させる。** 名前を読んで想像した挙動と実装がずれていたら、名前が間違っている。

- **戻り値を名前に出す。** エラーの配列を返すだけの関数を `validate*` と名付けない。集めて返すなら `collect*Errors`
- 探索していない関数に `find*` / `locate*` を使わない。その値を持つ新しい値を返すだけなら `with*`
- 公開APIも同じ基準で名付ける。「仕様書の語彙だから」を理由に、戻り値と食い違う名前を入口だけ残さない
- 1つのモジュール内で語彙を混在させない(内部だけ直して公開APIを残すと混在が復活する)

## その名前が既に別の意味を持っていないか確認する

**新しく付ける識別子名は、書く前にこのリポジトリの他の場所を探す。** 命名規約に沿っていても、
既存の接頭辞・仕様書が既にその語を別の意味で使っていることがある。接頭辞・語幹を grep し、
借りた慣習名がこの文脈で何を指すかを言えるか確かめ、比喩・抽象語は仕様書(`docs/`)に何回出るかを数える(0 回ならこのリポジトリの語彙に無い)。

## `And` を含む名前を作らない

`doAAndB` のような名前は、その関数が2つの振る舞いを持っている証拠。**名前を工夫して押し込めるのではなく、処理を分ける。** 分けられないなら、2つをまとめて表す1つの概念名を見つける(見つからないなら、やはり分けるべき処理)。

## 条件を組んだ式に名前を付ける

`&&` / `||` で2つ以上の条件を組んだ式を、`if` や JSX の中へそのまま置かない。**何を判定しているのかを表す名前の変数に入れてから使う。** 読み手は式を目で分解するまで、その分岐が何のためのものかを知れない。

```typescript
// NG: 何の判定かを式から読み解く必要がある
if (!isLoading && rows.length === 0) { /* ... */ }

// OK: 判定に名前がある
const showsEmptyState = !isLoading && rows.length === 0;
if (showsEmptyState) { /* ... */ }
```

- **条件が2つ以上要る理由がコードから読み取れないなら、変数のそばにコメントで残す**
- 名前が付けられないのは、その分岐で何をしたいのかが決まっていないサイン。条件を組み直す
- 単独の条件(`isEmpty` / `list.length === 0` など)はそのまま置いてよい。名前を増やすことが目的ではない

## 内容を表さない汎用語を使わない

`Entry` / `Info` / `Data` / `Detail` / `Manager` / `Helper` のような語は、何を指すのかを伝えない。ドメインの語彙で名付ける。

**名前が思いつかないのは、その型が2つの役割を抱き合わせているサイン**であることが多い。改名で解決しようとする前に役割を分けられないか確認する(分けた結果その型自体が不要になることもある)。

## 定数は PascalCase

**定数の名前に SCREAMING_SNAKE_CASE を使わない。** ここでの定数は、固定の値を名前で指すために置く `const`(符の基本値・牌の一覧・対応表など、SCREAMING_SNAKE_CASE で書きがちなもの)。オブジェクト・配列・スカラーのどれでも、また export の有無にもよらず PascalCase で書く。関数・コンポーネント・フック・計算結果を受けるローカル変数は対象外で、camelCase(コンポーネントは PascalCase)のまま。フレームワークが名前を決めている export(Next.js の `metadata` など)はその名前に従う。**コンパニオンオブジェクトのメンバー**も、値がオブジェクトでも同じ。コンパニオンのメンバーは公開 API としてメソッドと並ぶので、`Hoge.method()` と `Hoge.Member` で流儀を割らないため。

### 対応表のキーを PascalCase にするのは「キーが値の別名」のときだけ

データを引くための定数オブジェクトのキーは、**値が id や union の値そのもの**のとき(`Winds.Ton` の値は `"ton"`)だけ PascalCase。値が表示文字列・オブジェクトなど**別のもの**(`WindLabels.ton` の値は `"東"`)なら、キーは union の値をそのまま使う。

## ファイル名

- **ファイル名を関数名にしない。** ファイルはモジュールであり、その中の1関数の名前ではない。分割するときはモジュールとして意味のある名前を付ける
- **React の API 名をモジュール名にしない。** **何で実装したか**を指す名前は、器を差し替えたら嘘になる。フックは**返すもの**で名付ける
- `src/domains/` `src/services/` `features/` のモジュールフォルダはケバブケース + `index.ts`

## メソッド名を既存のドメインに揃える

コンパニオンオブジェクトのメソッド名は、既にあるドメインオブジェクトの語彙に合わせる。同じ意味の操作に別の名前を与えない。

- **値を組み立てるのは `create`。** 引数から新しい値を作る入口はこれに揃える
- **別の表現から作り直すのは `from*`。** 変換元を名前に出す。`create` と使い分ける基準は「引数がその値の材料か(`create`)、別の形で同じものを表しているか(`from*`)」
- **`of*` は使わない。** `create` / `from*` のどちらかに寄せる
- 判定は `is*` / `has*`、変換は `to*` / `*Value`、収集は `collect*`

## `utils/` のメソッドは動詞で始める

`src/utils/` の `<型名>Ex` は**組み込み型への操作**を集めた場所。メソッド名は**動詞、または結果そのものを表す語**で始める(`ArrayEx.insertAt` / `ArrayEx.sum`)。

- **`with*` はドメイン側の語彙。** 「その値を持つ新しい値」を返すコンパニオンオブジェクトのメソッドに使う。`utils/` へ持ち込むと、同じ層の中で語形が 2 通りに割れる
