ゴール:
- docs/spec-phase1.md の Part 1 に従い、4人麻雀・標準リーチ麻雀の点数計算エンジンを実装する。
- docs/spec-phase1.md の Part 2 に従い、ゲーム進行エンジンとCPU対局AIを実装する。
- docs/spec-match-screen.md に従い、対戦画面を実装する。対戦画面は結果を表示・入力するだけの画面ではなく、対戦開始から終局まで実際にCPUと対戦できること。
- 和了判定は通常形・七対子・国士無双に対応する。
- 役判定は 1〜13翻および役満に対応する。
- 符計算に対応する。
- 子/親、ツモ/ロン、本場・供託を含む点数計算に対応する。
- CLI として `echo '<入力JSON>' | pnpm --silent calc` で結果JSONを返せるようにする。
- 仕様に曖昧な点があれば、勝手に放置せず、判断と根拠を docs/assumptions.md に記録する。

入力JSON契約:
- docs/spec-phase1.md の「入力」に従う。
- hand は和了牌を含む純手牌。
- melds は副露。なければ空配列。
- winTile / winType / seatWind / roundWind / dora / uraDora / riichi / ippatsu / situational を扱う。
- 牌表記は `1m`〜`9m`, `1p`〜`9p`, `1s`〜`9s`, `ton/nan/sha/pei/haku/hatsu/chun`。
- 赤5は `0m/0p/0s` として扱う。

出力JSON契約:
- 和了時:
{
"valid": true,
"yaku": [{ "name": "pinfu", "han": 1 }],
"han": 3,
"fu": 30,
"score": {
"total": 5800,
"payments": [...]
}
}
- 和了不成立または役なし:
{ "valid": false, "reason": "no_yaku" | "not_winning_hand" | "invalid_input" }

採用ルール:
- 喰いタンあり。
- 後付けあり。
- 平和ツモは20符。
- 七対子は25符固定。
- 切り上げ満貫なし。
- 役満の複合あり。ダブル役満まで。
- 数え役満は13翻以上。
- 人和は採用しない。
- 緑一色に發は不要。發なし緑一色も役満。
- 複数解釈がある手は高点法、つまり最も点数が高くなる解釈を採用する。

ゲーム進行・CPU対局の実装要件:
- docs/spec-phase1.md の Part 2 に従う。
- 牌山生成・洗牌・配牌・王牌・ドラ表示牌を実装する。
- ツモ→打牌のターン進行を実装する。
- チー・ポン・カン・リーチ・ツモ・ロン・パスと、鳴きの優先順位(ロン > ポン/カン > チー)を実装する。
- リーチ・フリテン・流局・連荘/輪荘・東風/半荘の終了判定・順位決定を実装する。
- CPUは入門/標準/上級のレベルに応じて自動で打牌・鳴き・リーチ・和了を行う。
- CPUの行動は卓の公開情報と自分の手牌のみに基づいて決定する。他家の手牌や牌山の中身を参照しない。
- 和了時の点数計算は Part 1 の点数計算エンジンを再利用する。重複実装しない。

対戦画面の実装要件:
- Next.js App Router の画面として実装する。
- app/ は薄く保ち、画面本体は feature 配下へ配置する。
- docs/spec-match-screen.md の以下を画面に反映する。
- 対戦開始設定。
- 人間 / CPU の選択。
- CPUレベル: 入門 / 標準 / 上級。
- ルール設定: 東風戦 / 半荘戦、持ち点、返し点、喰いタン、後付け、赤ドラ、CPU自動和了。
- 初期表示: 東一局、0本場、供託0本、各家25,000点。
- 卓全体表示: 局、本場、供託、親。
- プレイヤー表示: 風、表示名、持ち点、親・子の状態。
- 対戦の進行: 対戦開始で配牌され、人間の手牌が表示される。手番が自動で進行し、CPUの手番ではCPUが自動で行動する。人間の手番では可能なアクション(打牌、チー、ポン、カン、リーチ、ツモ、ロン、パス)だけが操作可能になる。
- 対戦中の補助表示: 残り山枚数、ドラ表示牌、捨て牌河、鳴き面子、リーチ状態、現在の手番、操作可能アクション。
- 和了・流局結果の表示: 和了・流局は対局中の操作から自動的に発生する。手動で結果を入力する方式は採用しない。和了時は和了者、放銃者、和了種別、成立役、翻数、符、点数移動、親継続を表示する。
- 点数反映ルール。確定で点数反映のうえ次局へ進み、終了条件を満たすと最終順位を表示する。
- 画面は点数計算・ゲーム進行のドメインロジックを重複実装しない。
- 画面から計算・進行を呼び出す場合は、services / domains の公開APIを経由する。
- カスタムフックを作る場合は headless 原則に従い、JSXを返さない。
- props が増えすぎる場合は Composition パターンを使う。
- UI実装後は、可能なら Playwright などで表示確認し、スクリーンショットを取得する。

実装方針:
- TypeScript strict 前提で型を明確にする。
- 外部ランタイム依存は追加しない。Next.js / React 本体と devDependencies を除き、原則として依存追加は禁止。
- ドメインロジックはUIやNext.jsの層から分離する。
- イミュータブルな実装を優先する。特に domains 内では引数で受け取った配列・オブジェクトを破壊的に変更しない。
- import を try/catch で囲まない。
- テストしやすい純粋関数中心に設計する。
- サブエージェントの使用は許可する。必要であれば、以下のように並列化してよい。
- エージェントA: 牌・入力バリデーション・手牌分解・和了判定。
- エージェントB: 役判定。
- エージェントC: 符計算・点数計算。
- エージェントD: CLI契約・テスト整備。
- エージェントE: ゲーム進行エンジン・CPU対局AI。
- エージェントF: 対戦画面・UI状態・表示確認。
ただし、同じファイルを複数エージェントが同時に編集して競合させないこと。各エージェントには担当ファイル・責務を明示すること。
